# ADR-006: Wolverine как основной messaging-backbone (заменяет MediatR и MassTransit)

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В 2024–2025 годах .NET OSS-экосистема messaging-библиотек прошла через волну коммерциализации:

- **MediatR v13+** перешёл на лицензию RPL 1.5 (коммерческую). Бесплатное использование допускается только для организаций с выручкой менее $5 млн **и** привлечённым капиталом менее $10 млн.
- **MassTransit v9** стал коммерческим с тарифом от $400/мес.

До этих изменений стек Koto использовал MediatR для внутрипроцессной диспетчеризации команд и запросов, а MassTransit — для взаимодействия через внешние брокеры сообщений (RabbitMQ, Kafka). Кроме того, логика transactional outbox реализовывалась кастомно поверх MassTransit.

Коммерциализация обоих инструментов создала юридическую неопределённость по мере роста проектов, использующих Koto-стек. Возникла необходимость пересмотреть весь messaging-слой и найти единое MIT-лицензированное решение, способное покрыть оба сценария.

**Wolverine** (JasperFx Software, автор — Jeremy Miller) предлагает весь необходимый функционал в одной MIT-лицензированной библиотеке: внутрипроцессный медиатор, внешние транспорты, встроенный transactional outbox и поддержку Saga/process manager. Автор публично подтвердил намерение сохранять MIT-лицензию. По состоянию на 2026 год библиотека активно поддерживается (v5+), насчитывает ~2 100 звёзд на GitHub.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Внутрипроцессная диспетчеризация | Поддержка отправки команд и запросов обработчикам внутри одного процесса (замена MediatR) |
| Внешний транспорт | Поддержка публикации и потребления сообщений через RabbitMQ, Kafka, Azure Service Bus, AWS SQS |
| Transactional outbox | Встроенная гарантированная доставка через outbox-паттерн с интеграцией EF Core; не требует кастомной реализации |
| Saga / process manager | Поддержка долгоживущих бизнес-процессов, координирующих несколько сообщений |
| Kafka-транспорт | Поддержка Kafka через отдельный пакет `WolverineFx.Kafka` |
| Единая точка входа | Весь messaging (in-process и external) управляется одной библиотекой и одной конфигурацией |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Лицензия | Библиотека должна быть MIT-лицензированной без ограничений по выручке или капиталу | Обязательно |
| Производительность | Диспетчеризация должна быть не медленнее reflection-based MediatR; приветствуется source-generated dispatch | Высокая |
| Активная поддержка | Библиотека должна иметь регулярные релизы и отзывчивых мейнтейнеров | Высокая |
| Интеграция с EF Core | Outbox должен работать в рамках той же транзакции, что и запись доменных данных | Обязательно |
| Ясность ошибок | Известные баги (например, сломанная политика Requeue для Kafka) должны быть задокументированы и обойдены | Средняя |

---

## 3. Решение

### Описание

**Wolverine становится единственным messaging-backbone для Koto-стека, заменяя MediatR и MassTransit одновременно.**

Wolverine покрывает все три роли:

| Роль | Что заменяет | Механизм Wolverine |
|---|---|---|
| Внутрипроцессный медиатор | MediatR | `IMessageBus.InvokeAsync<T>` / `IMessageBus.SendAsync` с локальными обработчиками |
| Внешний message bus | MassTransit | Транспорты: `WolverineFx.RabbitMQ`, `WolverineFx.Kafka`, `WolverineFx.AzureServiceBus`, `WolverineFx.AmazonSqs` |
| Transactional outbox | Кастомные реализации | `WolverineFx.EntityFrameworkCore` с `AddOutboxMessageStorageToDatabase()` |

**Ключевые особенности реализации:**

- **Source-generated dispatch** — Wolverine генерирует диспетчерный код на этапе компиляции, что устраняет накладные расходы reflection-based подхода MediatR.
- **Обработчики** — конвенциональные: публичный класс с методом `Handle(TMessage)` без необходимости реализовывать интерфейс.
- **Kafka и политика ошибок** — политика `Requeue` для Kafka-транспорта содержит известный баг; для всех Kafka-обработчиков обязательно использовать DLQ (Dead Letter Queue) вместо Requeue.
- **MediatR v12 как запасной вариант** — MediatR v12 остаётся MIT-лицензированным без ограничений по выручке. Команды, предпочитающие более простую модель in-process dispatch, могут продолжать его использовать только для внутрипроцессных сценариев; Wolverine при этом используется исключительно для внешних транспортов и outbox.

Пример минимальной конфигурации с RabbitMQ и outbox:

```csharp
builder.Host.UseWolverine(opts =>
{
    // Внешний транспорт — RabbitMQ
    opts.UseRabbitMq(new Uri(builder.Configuration["RabbitMq:Uri"]!))
        .AutoProvision();

    // Transactional outbox через EF Core
    opts.Policies.UseNpgsqlTransactionalOutboxOnAllSendingEndpoints();
});

builder.Services.AddDbContext<AppDbContext>(/* ... */);
builder.Services.AddWolverineEntityFrameworkCoreSupport<AppDbContext>();
```

Пример обработчика команды (без интерфейса, конвенция по имени метода):

```csharp
public class PlaceOrderHandler
{
    private readonly AppDbContext _db;

    public PlaceOrderHandler(AppDbContext db) => _db = db;

    public async Task Handle(PlaceOrderCommand command, IMessageBus bus)
    {
        var order = Order.Place(command.CustomerId, command.Items);
        _db.Orders.Add(order);
        // Outbox: сообщение будет отправлено атомарно вместе с SaveChanges
        await bus.PublishAsync(new OrderPlacedEvent(order.Id));
        await _db.SaveChangesAsync();
    }
}
```

Пример Kafka-конфигурации с обязательным DLQ:

```csharp
opts.UseKafka(builder.Configuration["Kafka:BootstrapServers"]!)
    .ConfigureConsumers(consumer =>
    {
        // ВАЖНО: политика Requeue сломана для Kafka — используем только DLQ
        consumer.OnFailure.MoveToDeadLetterQueue();
    });
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Единая MIT-лицензия | Wolverine покрывает все messaging-сценарии под MIT без ограничений по выручке или капиталу, устраняя юридическую неопределённость от MediatR v13+ и MassTransit v9 |
| Сокращение числа зависимостей | Один пакет вместо двух (MediatR + MassTransit) упрощает граф зависимостей, конфигурацию и мониторинг |
| Встроенный outbox | Transactional outbox поставляется из коробки и интегрируется с EF Core без кастомного кода; гарантирует атомарность записи данных и публикации событий |
| Производительность | Source-generated dispatch быстрее reflection-based MediatR; критично для высоконагруженных обработчиков команд |
| Полный охват транспортов | RabbitMQ, Kafka, Azure Service Bus, AWS SQS — все приоритетные брокеры поддерживаются без дополнительных абстракций |
| Активное развитие | v5+ в 2026 году, регулярные релизы, публичное обязательство автора по MIT-лицензии |
| Saga-поддержка | Встроенная поддержка Saga/process manager устраняет необходимость во внешних решениях для оркестрации долгоживущих процессов |

#### Последствия

**Положительные:**
- Весь messaging-стек управляется единым API и единой конфигурацией.
- Устранена юридическая неопределённость, связанная с коммерциализацией MediatR и MassTransit.
- Transactional outbox работает из коробки — исключены возможные ошибки в кастомных реализациях.
- Source-generated dispatch снижает накладные расходы на диспетчеризацию.
- Уменьшение числа зависимостей упрощает аудит безопасности и supply chain.

**Негативные:**
- Сообщество Wolverine значительно меньше, чем у MassTransit (2 100 vs 7 700 звёзд): меньше готовых ответов на Stack Overflow и сторонних примеров.
- Сильная зависимость от основного автора (Jeremy Miller): замедление или прекращение его участия несёт риск для проекта.
- Известный баг политики Requeue для Kafka требует явного использования DLQ — команды должны быть об этом осведомлены.
- Wolverine менее испытан при экстремальных enterprise-нагрузках в сравнении с MassTransit v8.
- Миграция с MediatR и MassTransit требует рефакторинга существующих обработчиков и конфигурации.

**Зависимости:**
- `Koto.Application` — пакет для внутрипроцессной диспетчеризации; переходит на Wolverine-обработчики вместо `IRequestHandler<>`.
- `Koto.Infrastructure` — пакет для внешних транспортов и outbox; конфигурирует Wolverine-транспорты.
- Все сервисы, использующие Koto-стек, должны добавить `UseWolverine()` в хост и соответствующие транспортные пакеты.
- MediatR v12 может оставаться как дополнительная зависимость в командах, выбравших запасной вариант для in-process dispatch.

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **MediatR v12 + MassTransit v8** | Последние свободные версии; хорошо знакомы команде; большое сообщество | Технический долг накапливается по мере того, как сообщество переходит на коммерческие версии; два отдельных инструмента; кастомный outbox остаётся; нет гарантий MIT для будущих патчей | Компромисс «заморозить на последней бесплатной версии» — временное решение, не устраняющее системный риск |
| **MassTransit v9 (коммерческий)** | Крупнейшее сообщество в .NET messaging; максимальная battle-tested надёжность; богатая экосистема | От $400/мес; коммерческая лицензия с ограничениями; требует MediatR отдельно для in-process | Коммерческая лицензия противоречит требованию MIT для Koto-стека |
| **Rebus (MIT)** | MIT-лицензия; хороший message bus; простой API | Нет встроенного медиатора; нет встроенного outbox; потребует MediatR рядом | Не покрывает in-process dispatch; не устраняет необходимость в двух библиотеках |
| **Brighter (MIT)** | MIT-лицензия; CQRS + messaging в одном; поддержка outbox | Меньшая экосистема; менее активная поддержка; слабее документирован | Меньше транспортных интеграций; более высокий риск заброшенности по сравнению с Wolverine |
| **NServiceBus** | Максимально enterprise-зрелый; профессиональная поддержка | Всегда коммерческий; не бесплатен для production | Коммерческая лицензия не приемлема |

### 5. Риски

1. **Зависимость от единственного ключевого автора**  
   Wolverine разрабатывается преимущественно Jeremy Miller. Замедление его участия или уход из проекта создаёт риск стагнации.  
   *Меры:* Отслеживать активность репозитория (коммиты, релизы) на ежеквартальной основе. При снижении активности инициировать пересмотр ADR. Рассмотреть возможность корпоративного спонсирования JasperFx Software для снижения зависимости.

2. **Малое сообщество и дефицит готовых решений**  
   При возникновении нестандартных проблем сообщество Wolverine (~2 100 звёзд) предложит меньше готовых ответов, чем MassTransit (~7 700 звёзд).  
   *Меры:* Формировать внутреннюю базу знаний по Wolverine в Koto-документации. Выделить ответственного за мониторинг GitHub Issues и Discord-канала Wolverine.

3. **Известный баг Requeue в Kafka-транспорте**  
   Политика Requeue не работает корректно с Kafka: сообщения могут быть потеряны или обработаны некорректно при повторной постановке в очередь.  
   *Меры:* Запретить политику Requeue для всех Kafka-обработчиков через линтер/code review checklist. Всегда использовать DLQ. Зафиксировать ограничение в `CONTRIBUTING.md` и в Koto-примерах. Периодически проверять, устранён ли баг в новых версиях Wolverine.

4. **Риск смены лицензии**  
   Wolverine сегодня MIT, однако в 2024–2025 гг. прецеденты MediatR и MassTransit показали, что смена лицензии возможна даже у уважаемых авторов.  
   *Меры:* Зафиксировать текущую MIT-версию в lock-файлах. Настроить автоматическую проверку лицензий в CI (например, `dotnet-license-checker`). При смене лицензии немедленно инициировать пересмотр ADR; MediatR v12 + MassTransit v8 рассматриваются как запасной вариант «заморозки».

5. **Недостаточная проверка при экстремальных нагрузках**  
   MassTransit v8 имеет многолетнюю историю эксплуатации при высоких нагрузках; Wolverine пока менее испытан в крайних enterprise-сценариях.  
   *Меры:* Провести нагрузочное тестирование ключевых Wolverine-обработчиков до выхода в production с высоким трафиком. Начинать с некритичных потоков сообщений при первичном внедрении. Документировать результаты нагрузочных тестов в Koto-репозитории.
