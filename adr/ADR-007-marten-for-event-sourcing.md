# ADR-007: Marten (PostgreSQL) для Event Sourcing вместо EventStoreDB/KurrentDB

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В рамках Koto-стека необходимо выбрать механизм хранения событий для реализации Event Sourcing в .NET-сервисах. Были рассмотрены три варианта:

1. **EventStoreDB (ныне KurrentDB)** — специализированное хранилище событий, изначально созданное под Event Sourcing.
2. **Marten** — библиотека для .NET, использующая PostgreSQL как документное хранилище и хранилище событий одновременно.
3. **SqlStreamStore** — архивирован в августе 2024 года; использование недопустимо.

Критическим фактором стало **изменение лицензии EventStoreDB**:

- Версии **v23.10 и ранее** распространялись под разрешительной лицензией с открытым исходным кодом.
- Начиная с **v24.10 LTS** применяется лицензия **ESLv2 (Event Store License v2)** — аналог Elastic License v2.
- ESLv2 **не является** лицензией с открытым исходным кодом по стандартам OSI.
- Самостоятельный деплой для внутренних задач формально допустим, однако управление EventStoreDB как сервисом (managed service) запрещено.
- Поддержка v23.10 LTS **истекает в октябре 2025 года** — без пути обновления, который не требовал бы принятия ESLv2.

Команды уже эксплуатируют PostgreSQL в продакшене; новая инфраструктура нежелательна.

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Хранение событий | Хранилище должно поддерживать добавление, чтение и подписку на потоки событий (event streams) |
| Проекции | Должна быть встроенная инфраструктура для построения проекций (read models) из событий |
| Фоновая обработка | Проекции должны строиться асинхронно, не блокируя запись событий |
| Документное хранилище | Возможность хранить проекции как документы в том же хранилище, что и события |
| Интеграция с .NET | Нативная интеграция с экосистемой .NET: DI, транзакции, типизированные сессии |
| Совместная работа с EF Core | Должна быть возможность использовать Marten и EF Core в одном сервисе на одной БД PostgreSQL |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Лицензия | Лицензия должна быть OSI-совместимой и не иметь рисков изменения в ближайшие годы | Обязательно |
| Инфраструктура | Не должно требоваться новых компонентов инфраструктуры помимо уже используемого PostgreSQL | Высокая |
| Сопровождаемость | Проект должен активно поддерживаться и иметь документированную дорожную карту | Высокая |
| Экосистема | Желательна согласованность с другими компонентами Koto-стека (Wolverine) | Средняя |
| Операционная нагрузка | Команды не должны обслуживать отдельный кластер хранилища событий | Высокая |

## 3. Решение

### Описание

**Для Event Sourcing в Koto-стеке используется Marten с PostgreSQL в качестве хранилища событий.**

Marten предоставляет полноценный event store поверх PostgreSQL: таблицы `mt_events` и `mt_streams` управляются самой библиотекой. Проекции (read models) могут храниться как документы в тех же PostgreSQL-таблицах. Async Daemon — встроенный фоновый обработчик — строит проекции асинхронно.

В одном сервисе допускается одновременное использование Marten и EF Core на одной базе данных PostgreSQL:

- **Marten** управляет потоками событий (`mt_events`, `mt_streams`).
- **EF Core** управляет read models, конфигурационными таблицами и outbox-таблицами.
- Оба инструмента используют раздельное управление соединениями, но работают с одной и той же базой данных. Это явно задокументированный и поддерживаемый паттерн.

```csharp
// Регистрация Marten в одном сервисе с EF Core
builder.Services.AddMarten(opts =>
{
    opts.Connection(connectionString);
    opts.Events.AddEventType<OrderPlaced>();
    opts.Events.AddEventType<OrderShipped>();

    // Inline-проекция: строится синхронно при записи события
    opts.Projections.Add<OrderSummaryProjection>(ProjectionLifecycle.Inline);

    // Async-проекция: строится фоновым Async Daemon
    opts.Projections.Add<OrderAuditLogProjection>(ProjectionLifecycle.Async);
})
.UseLightweightSessions()
.AddAsyncDaemon(DaemonMode.HotCold); // HA-режим для нескольких инстансов

// EF Core на той же PostgreSQL-базе — без конфликтов
builder.Services.AddDbContext<ReadModelDbContext>(opts =>
    opts.UseNpgsql(connectionString));
```

```csharp
// Запись события через Marten IDocumentSession
public async Task<Result<OrderId>> PlaceOrderAsync(PlaceOrderCommand cmd)
{
    var order = Order.Place(cmd.CustomerId, cmd.Items);

    await using var session = store.LightweightSession();
    session.Events.StartStream<Order>(order.Id, order.DomainEvents);
    await session.SaveChangesAsync();

    return Result<OrderId>.Success(order.Id);
}
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Лицензия MIT | Marten распространяется под лицензией MIT. Нет рисков, аналогичных ESLv2 EventStoreDB. Лицензия контролируется JasperFx, организацией с открытым исходным кодом |
| Нет новой инфраструктуры | PostgreSQL уже эксплуатируется командами. Marten не требует отдельного кластера, отдельных операционных процедур или новых знаний у DevOps |
| Единый стек с Wolverine | JasperFx развивает оба проекта: Wolverine (messaging) и Marten (persistence). «Critter Stack» — согласованная, хорошо задокументированная комбинация с совместными release notes |
| Async Daemon | Встроенный фоновый обработчик для асинхронного построения проекций. Поддерживает HA-режим (HotCold) для нескольких инстансов без сторонних координаторов |
| Event store + document store | Marten позволяет хранить и события, и проекции в PostgreSQL, избегая необходимости в отдельном Redis или другом хранилище read models |
| Совместимость с EF Core | Явно поддерживаемый паттерн: Marten и EF Core работают в одном сервисе на одной БД. Marten берёт события, EF Core — read models и outbox |
| Активное развитие | v8+ (2026) активно поддерживается; 3 400+ звёзд на GitHub; регулярные релизы |

#### Последствия

**✅ Положительные:**
- Никакой новой инфраструктуры: весь Koto-стек продолжает работать на PostgreSQL.
- Лицензия MIT исключает сценарий принудительной миграции под коммерческую лицензию.
- Async Daemon закрывает задачу асинхронных проекций «из коробки» — не нужно строить собственный механизм.
- Единая экосистема JasperFx (Wolverine + Marten) упрощает интеграцию транзакционного outbox и обработки сообщений.
- Команды применяют уже знакомые инструменты мониторинга, бэкапа и масштабирования PostgreSQL.
- EF Core и Marten сосуществуют без архитектурных компромиссов.

**⚠️ Негативные:**
- Marten — не специализированный event store; некоторые advanced-возможности EventStoreDB (persistent subscriptions, competing consumers) реализуются иначе или через Wolverine.
- Производительность при очень больших объёмах событий ограничена возможностями PostgreSQL: нет встроенного partitioning событий — его нужно настраивать вручную.
- Команды должны понимать модель Marten (sessions, unit of work, projection lifecycle), что требует onboarding.

**↗️ Зависимости:**
- Выбор Marten предполагает использование PostgreSQL как обязательного компонента инфраструктуры для всех сервисов с Event Sourcing.
- Сервисы, использующие Marten, получают транзитивную зависимость от `Marten` NuGet-пакета — это допустимо на уровне `Koto.Persistence` и сервисов, но не на уровне `Koto.Domain` (см. ADR-001).
- Решение об использовании Async Daemon требует обеспечения HA-режима (HotCold) при деплое нескольких реплик сервиса.
- Совместное использование с Wolverine рекомендуется, но не является обязательным условием.

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **EventStoreDB v23.10 (старая лицензия)** | Специализированный event store; богатые возможности подписок; зрелый продукт | Поддержка LTS истекает в октябре 2025 года; нет пути обновления без ESLv2; отдельная инфраструктура | Критический лицензионный риск после октября 2025; вынужденная миграция на ESLv2 неприемлема |
| **EventStoreDB v24.10+ (ESLv2 / KurrentDB)** | Специализированный event store; активно развивается | ESLv2 не является OSI-совместимым открытым исходным кодом; запрет на managed service; отдельная инфраструктура; зависимость от коммерческих решений вендора | Не является истинным open source; операционная нагрузка; недопустимая зависимость от вендорской лицензионной политики |
| **SqlStreamStore** | Минималистичный; PostgreSQL/SQL Server как бэкенд | Архивирован в августе 2024 года; без поддержки и исправлений безопасности | Мёртвый проект; использование категорически недопустимо |
| **Собственная таблица событий в PostgreSQL** | Полный контроль; никаких зависимостей | Необходимо самостоятельно реализовывать версионирование, оптимистичный concurrency, проекции, подписки и снапшоты | Reinventing the wheel без инфраструктуры проекций; неоправданные трудозатраты |
| **EF Core как хранилище событий** | Команды уже знают EF Core; один инструмент | Нет встроенной поддержки потоков событий, оптимистичного concurrency по версии, проекций и подписок | Возможно технически, но отсутствует вся инфраструктура Event Sourcing; Marten делает это лучше |

### 5. Риски

1. **Лицензионный риск Marten**  
   *Описание:* JasperFx теоретически может сменить лицензию Marten в будущем (прецедент — MediatR, MassTransit, EventStoreDB).  
   *Меры:* Отслеживать GitHub-репозиторий Marten на предмет изменений в `LICENSE`. При любом изменении лицензии инициировать отдельный ADR. Архитектура изолирует зависимость от Marten на уровне `Koto.Persistence` — замена потребует изменений только в одном слое.

2. **Производительность при высоких нагрузках**  
   *Описание:* PostgreSQL не является специализированным журналом событий; при больших объёмах (`>100M` событий) возможны деградации производительности записи и чтения.  
   *Меры:* Настроить партиционирование таблицы `mt_events` по дате или по типу агрегата. Использовать снапшоты (snapshots) для длинных потоков событий. Мониторить размер таблиц и время построения проекций. При превышении порогов — отдельный ADR с пересмотром решения.

3. **Сложность Async Daemon в HA-среде**  
   *Описание:* При деплое нескольких реплик сервиса Async Daemon в режиме HotCold требует корректной конфигурации лидерных выборов через PostgreSQL advisory locks.  
   *Меры:* Следовать официальной документации Marten по HotCold-режиму. Покрыть интеграционными тестами сценарии переключения лидера. Включить метрики Async Daemon в систему мониторинга.

4. **Кривая обучения команд**  
   *Описание:* Разработчики, не знакомые с Event Sourcing или Marten, могут допускать ошибки в управлении сессиями, жизненным циклом проекций и конкурентным доступом.  
   *Меры:* Подготовить внутренний гайд «Getting Started with Marten in Koto» со ссылкой на настоящий ADR. Провести onboarding-сессии. Добавить примеры использования в `Koto.Samples`.

5. **Конфликты транзакций между Marten и EF Core**  
   *Описание:* Некорректное использование транзакций может привести к частичной записи событий без соответствующего обновления read model или наоборот.  
   *Меры:* Использовать паттерн transactional outbox через Wolverine для координации между Marten и EF Core. Документировать допустимые паттерны транзакций в CONTRIBUTING.md.
