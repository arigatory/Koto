# ADR-020: Транспорт-независимый Result→HTTP маппинг в Koto.Api.AspNetCore

**Статус:** ✅ Принято  
**Дата:** 2026-07-04  

---

## 1. Контекст

До v0.3.0 маппинг `Result<T>` → HTTP-ответ существовал только внутри `Koto.Api.FastEndpoints` (`KotoProblemDetails` + захардкоженный `StatusCodeFrom`). Это создавало две проблемы:

1. **Потребители не на FastEndpoints оставались без маппинга.** Реальный кейс — IceFlow: MVC-контроллеры, ~43 ручных `Result.Match(...)` с разбросанными по API-слою строковыми сравнениями `Error.Code` для выбора HTTP-статуса. То же ждало бы любого потребителя на Minimal API.
2. **Захардкоженный маппинг был потерянным (lossy).** `StatusCodeFrom` знал только `*.not-found` → 404, `*.already-*` → 409, `general.value.*` → 400, а **всё остальное отправлял в 500**. Доменные ошибки валидации (`general.invalid-length`, `general.collection-is-too-small`) и любые бизнес-коды (`orders.order.payment-failed`) превращались в 500 Internal Server Error — сервер объявлял свою вину там, где клиент нарушил бизнес-правило. Расширить таблицу без форка пакета было невозможно.

ADR-003 постулирует: маппинг «код → HTTP-статус» — ответственность инфраструктурного слоя, реализуемая строковыми паттернами. Нужна библиотечная реализация этого маппинга, доступная всем HTTP-транспортам ASP.NET Core.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Транспорт-независимость | Маппинг работает из Minimal API (`IResult`), MVC (`ActionResult`) и FastEndpoints |
| Расширяемость | Потребитель регистрирует свои соответствия код → статус без форка пакета |
| Multi-error | Несколько ошибок `Result.Errors` отдаются как validation problem details (RFC 7807) с группировкой по `Error.Field` |
| Структурные расширения | Ответ содержит `errorCode`/`errorCodes` и (при наличии) `correlationId` extensions |
| Честный fallback | Незамапленный бизнес-код — ошибка клиента (422), а не сервера (500) |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Минимум зависимостей | Только `Koto.Domain` + `FrameworkReference Microsoft.AspNetCore.App` | Обязательно |
| Доменная чистота | `Koto.Domain` не знает об HTTP (ADR-003 NF2 сохраняется) | Обязательно |
| Pit of success | Работает без регистрации (дефолтная таблица), настройка — один вызов `AddKotoAspNetCore(o => …)` | Высокая |

---

## 3. Решение

### Описание

**Новый пакет `Koto.Api.AspNetCore`** — транспорт-независимый Result→HTTP слой. Состав:

| Тип | Назначение |
|---|---|
| `KotoHttpErrorOptions` | Расширяемый registry `Error.Code` → HTTP-статус. Приоритет: exact code → custom rules (`Func<Error,int?>`) → suffix → prefix → `Field != null` → 400 → `FallbackStatusCode` (422). Пользовательские правила имеют приоритет над встроенными в своей категории |
| `KotoProblemDetails` | Фабрика RFC 7807: одна ошибка → `ProblemDetails` (+ `errorCode`, `field`, `correlationId` extensions); несколько → `HttpValidationProblemDetails` с `errors` по `Error.Field` + `errorCodes` |
| `ToHttpResult` / `ToHttpResultAsync` | `Result<T>` → `IResult` для Minimal API (200/204 или problem) |
| `ToActionResult` / `ToActionResultAsync` | `Result<T>` → `ActionResult<T>` для MVC-контроллеров |
| `AddKotoAspNetCore(Action<KotoHttpErrorOptions>?)` | Регистрация registry в DI |

Встроенная таблица: `.not-found` → 404, `.already-*`/`.conflict` → 409, `.unauthorized` → 401, `.forbidden` → 403, `general.*`/`validation.*`/`Field != null` → 400, остальное → **422**.

**Fallback 422, а не 500:** проваленный `Result` — это видимое клиенту нарушение бизнес-правила, на которое клиент может отреагировать; 500 зарезервирован за необработанными исключениями (`GlobalExceptionHandler`).

**`Koto.Api.FastEndpoints` переиспользует пакет:** собственный `KotoProblemDetails` удалён, `AddKotoApi(configureErrors)` вызывает `AddKotoAspNetCore`, эндпоинты отдают все ошибки `Result.Errors` (не только первую).

### Аргументация

| Критерий | Обоснование |
|---|---|
| Отдельный пакет | ASP.NET Core-зависимость не попадает ни в `Koto.Domain`, ни в потребителей, которым HTTP-слой не нужен |
| Registry вместо switch | Потребитель расширяет маппинг данными (`Map`, `MapSuffix`, `MapPrefix`, предикаты), а не форком кода; тестируется изолированно |
| 422 fallback | Бизнес-ошибки перестают маскироваться под сбои сервера; мониторинг 5xx снова означает реальные инциденты |
| Multi-error → validation problem details | Стандартный формат RFC 7807, который клиенты (формы) понимают из коробки: ошибки по полям |

#### Последствия

**Положительные:**
- MVC- и Minimal API-потребители убирают ручной `Match`-boilerplate (IceFlow: ~43 места).
- Один источник истины для маппинга статусов во всех транспортах.
- Незамапленные бизнес-коды больше не создают ложных 500 в мониторинге.

**Негативные:**
- Ещё один пакет в наборе (принято: зависимость минимальна и опциональна).
- Breaking change для потребителей FastEndpoints: namespace `KotoProblemDetails` изменился, `StatusCodeFrom` заменён на `KotoHttpErrorOptions`, незамапленные коды теперь 422 (было 500).

**Зависимости:**
- `Koto.Api.FastEndpoints` теперь ссылается на `Koto.Api.AspNetCore`.
- Коды ошибок должны следовать dot-notation из ADR-003, иначе дефолтная таблица не сработает и применится fallback.

## 4. Альтернативы

| Вариант | Причина отклонения |
|---|---|
| Оставить маппинг только в FastEndpoints (статус-кво) | MVC/Minimal API потребители пишут ручной `Match` и дублируют выбор статусов строковыми сравнениями (реальный кейс IceFlow — ~43 ручных `Match`); захардкоженную таблицу нельзя расширить |
| Встроить маппинг в `Koto.Domain` | Тянет `FrameworkReference Microsoft.AspNetCore.App` в домен; нарушает ADR-001 (zero external deps) и ADR-003 (домен не знает про HTTP) |
| Встроить в `Koto.Application` | Тот же конфликт: `Koto.Application` — только интерфейсы без инфраструктурных зависимостей |
| Fallback 400 вместо 422 | 400 семантически означает «синтаксически некорректный запрос»; 422 точнее для валидного запроса, нарушающего бизнес-правило |
| Fallback 500 (как было) | Бизнес-ошибка — не сбой сервера: ложные алерты в мониторинге 5xx, клиент не понимает, что запрос можно исправить |

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Потребитель полагается на старое поведение «неизвестный код → 500» | Низкая | Среднее | Migration note в PLAN.md; `FallbackStatusCode` настраивается одной строкой |
| Расхождение дефолтной таблицы с фактическими кодами сервиса | Средняя | Среднее | Registry расширяем; тесты пакета фиксируют таблицу; соглашение dot-notation из ADR-003 |
| Дублирование правил между сервисами | Средняя | Низкое | Общие правила выносятся в shared-метод конфигурации options внутри сервиса-потребителя |
