# ADR-013: Transactional Outbox через встроенную интеграцию Wolverine с EF Core

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В распределённых системах, основанных на событийной архитектуре, критически важно атомарно сохранять бизнес-данные и гарантировать доставку событий. Наивная реализация с двумя последовательными операциями создаёт проблему двойной записи (dual-write problem):

```csharp
// НЕВЕРНО — не атомарно:
await _db.SaveChangesAsync();        // заказ сохранён ✓
await _kafkaProducer.PublishAsync();  // падение здесь → заказ есть, событие потеряно!

// ИЛИ:
await _kafkaProducer.PublishAsync();  // событие опубликовано ✓
await _db.SaveChangesAsync();         // падение здесь → событие есть, заказ не сохранён!
```

Любой из этих сценариев приводит к рассогласованию состояния между сервисами: либо событие теряется (подписчики не узнают об изменении), либо событие публикуется для несуществующих данных (подписчики получают «призрачное» уведомление).

Паттерн Transactional Outbox решает эту проблему: сообщения сохраняются в ту же транзакцию базы данных, что и бизнес-данные, а отдельный фоновый процесс надёжно доставляет их брокеру сообщений.

Wolverine предоставляет `AddWolverineDbContext<TContext>()` — обёртку над EF Core, которая перехватывает `SaveChangesAsync` и автоматически записывает доменные события в outbox-таблицу (`wolverine_outgoing_envelopes`) в рамках единой транзакции с бизнес-данными. Это устраняет необходимость писать и поддерживать кастомную реализацию outbox.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Атомарность | Сохранение бизнес-данных и запись событий в outbox должны происходить в одной транзакции БД |
| Сбор доменных событий | События должны собираться из агрегатов, отслеживаемых EF Core change tracker, без ручного вызова |
| Гарантированная доставка | Доставленность события не должна зависеть от доступности брокера в момент вызова `SaveChangesAsync` |
| Повторная доставка | При сбое доставки фоновый процесс должен повторять попытки с экспоненциальной задержкой |
| Dead Letter Queue | Сообщения, которые не удалось доставить после исчерпания попыток, должны направляться в DLQ |
| Публикация интеграционных событий | Обработчик может дополнительно публиковать интеграционные события в Kafka из доменных событий |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Надёжность | Гарантия at-least-once доставки; потеря сообщений недопустима | Обязательно |
| Идемпотентность потребителей | Потребители должны быть готовы к дублирующимся сообщениям и обрабатывать их без побочных эффектов | Обязательно |
| Производительность | Перехват `SaveChangesAsync` не должен ощутимо увеличивать задержку операций записи | Высокая |
| Наблюдаемость | Метрики outbox-лага должны быть доступны для мониторинга и алертинга | Высокая |
| Минимум кода для поддержки | Решение не должно требовать кастомного polling-сервиса или ручной сериализации событий | Средняя |

## 3. Решение

### Описание

**Wolverine Transactional Outbox с интеграцией EF Core становится стандартным механизмом гарантированной доставки событий в Koto-стеке.**

Регистрация `AddWolverineDbContext<TContext>()` вместо стандартного `AddDbContext<TContext>()` включает автоматический перехват `SaveChangesAsync`. Поток выполнения выглядит следующим образом:

```
Вызов SaveChangesAsync():
  1. EF Core записывает бизнес-данные в свои таблицы
  2. Перехватчик KotoDbContext собирает доменные события из отслеживаемых агрегатов
  3. Wolverine сериализует доменные события и записывает их в таблицу outbox
  → Всё в ОДНОЙ транзакции БД → АТОМАРНО

Фоновый процесс Wolverine (асинхронно):
  4. Читает записи из outbox-таблицы
  5. Доставляет доменные события внутрипроцессным обработчикам
  6. Обработчик может публиковать интеграционные события в Kafka
  7. Помечает записи outbox как доставленные
  8. При сбое: повторные попытки с экспоненциальной задержкой, затем DLQ
```

Пример конфигурации:

```csharp
// Program.cs
builder.Host.UseWolverine(opts =>
{
    opts.UseKafka(builder.Configuration["Kafka:BootstrapServers"]!)
        .ConfigureConsumers(consumer =>
        {
            // ВАЖНО: политика Requeue сломана для Kafka — только DLQ
            consumer.OnFailure.MoveToDeadLetterQueue();
        });

    // Включает outbox для всех исходящих эндпоинтов
    opts.Policies.UseNpgsqlTransactionalOutboxOnAllSendingEndpoints();
});

// Wolverine-обёртка вместо стандартного AddDbContext
builder.Services.AddWolverineDbContext<KotoDbContext>(
    o => o.UseNpgsql(builder.Configuration.GetConnectionString("Default")));
```

Пример обработчика, демонстрирующего атомарность:

```csharp
public class PlaceOrderHandler
{
    private readonly KotoDbContext _db;

    public PlaceOrderHandler(KotoDbContext db) => _db = db;

    public async Task Handle(PlaceOrderCommand command)
    {
        var order = Order.Place(command.CustomerId, command.Items);
        _db.Orders.Add(order);

        // SaveChangesAsync атомарно:
        //  — записывает Order в таблицу Orders
        //  — записывает OrderPlacedEvent в wolverine_outgoing_envelopes
        await _db.SaveChangesAsync();
    }
}

// Отдельный обработчик доменного события публикует интеграционное событие в Kafka
public class OrderPlacedEventHandler
{
    public async Task Handle(OrderPlacedEvent evt, IMessageBus bus)
    {
        await bus.PublishAsync(new OrderCreatedIntegrationEvent(evt.OrderId));
    }
}
```

Wolverine экспонирует метрику outbox-лага, позволяя настроить алерт при зависании сообщений:

```
wolverine_outgoing_envelopes_total{status="outstanding"} > 100 → ALERT
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Атомарность через единую транзакцию | `AddWolverineDbContext<T>` перехватывает `SaveChangesAsync` и записывает события в outbox в той же транзакции — проблема dual-write устранена на уровне фреймворка |
| Production-ready без кастомного кода | Wolverine обрабатывает ретраи, backoff, DLQ и мониторинг из коробки; не нужно писать и поддерживать polling BackgroundService |
| Согласованность с ADR-006 | Wolverine уже принят как messaging-backbone; использование его встроенного outbox не добавляет новых зависимостей |
| MIT-лицензия | Wolverine остаётся MIT, что соответствует требованию лицензионной чистоты Koto-стека |
| Встроенная наблюдаемость | Метрики outbox-лага позволяют выявлять зависшие сообщения без дополнительной инструментации |
| Идемпотентность как явный контракт | At-least-once семантика явно закрепляет ответственность потребителей за идемпотентность, что является правильной практикой для распределённых систем |

#### Последствия

**Положительные:**
- Устранена проблема dual-write: бизнес-данные и сообщения всегда согласованы.
- Нет кастомного polling-сервиса — меньше кода, меньше поверхности для ошибок.
- Ретраи, backoff и DLQ работают из коробки — повышена надёжность доставки.
- Мониторинг outbox-лага позволяет оперативно реагировать на сбои доставки.
- Поток «доменное событие → внутренний обработчик → интеграционное событие в Kafka» чётко разделяет ответственности между слоями.

**Негативные:**
- Все потребители обязаны реализовывать идемпотентность (at-least-once гарантия означает возможность дублей).
- Замена `AddDbContext` на `AddWolverineDbContext` требует точечного рефакторинга регистрации контекстов.
- При сбое фонового процесса доставки возникает задержка между сохранением события и его обработкой (eventual consistency).
- Известный баг политики Requeue для Kafka-транспорта (см. ADR-006) остаётся в силе: обязательно использовать DLQ.

**Зависимости:**
- `Koto.Infrastructure` — пакет, в котором регистрируется `AddWolverineDbContext<T>` и настраивается outbox-политика.
- `Koto.Domain` — агрегаты должны накапливать доменные события во внутренней коллекции, доступной EF Core change tracker через перехватчик.
- ADR-006 (Wolverine как messaging-backbone) — настоящее решение является расширением принятого в ADR-006 выбора и не может применяться без него.
- Все сервисы, использующие outbox, обязаны иметь применённые EF Core миграции для создания таблицы `wolverine_outgoing_envelopes`.

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Кастомный outbox с BackgroundService** | Полный контроль над реализацией; нет зависимости от Wolverine internals | Нужно писать и поддерживать polling-сервис, сериализацию, ретраи, DLQ — значительный объём кастомного кода | Wolverine предоставляет ту же функциональность production-ready «из коробки»; дублирование усилий нецелесообразно |
| **Change Data Capture (Debezium)** | Не требует изменений в коде приложения; работает на уровне WAL БД; высокая пропускная способность | Требует развёртывания и поддержки Kafka Connect + Debezium; усложняет операционный стек; затрудняет локальную разработку | Дополнительная инфраструктурная сложность избыточна при наличии встроенного outbox в Wolverine |
| **Двухфазная фиксация (2PC)** | Теоретически гарантирует атомарность между БД и брокером | Антипаттерн в микросервисах: не масштабируется, требует XA-транзакций, большинство брокеров не поддерживают 2PC | Не применимо в современной микросервисной архитектуре |
| **«Публикуй перед сохранением»** | Простота реализации | Не атомарно: при падении `SaveChangesAsync` событие уже опубликовано → дублирующаяся обработка без сохранённых данных | Риск рассогласования состояния выше, чем при подходе «сначала сохрани» |
| **MassTransit v8 Outbox** | Зрелая реализация; хорошо документирована | MassTransit v9 коммерческий; v8 не получает новых функций; требует отдельного пакета параллельно с Wolverine | Противоречит решению ADR-006 использовать Wolverine как единственный messaging-backbone |

### 5. Риски

1. **Нарушение идемпотентности потребителями**  
   At-least-once семантика гарантирует доставку, но не защищает от дублей. Потребитель, не реализующий идемпотентность, может обработать одно событие дважды и привести к рассогласованию данных.  
   *Меры:* Зафиксировать требование идемпотентности в `CONTRIBUTING.md` и Koto-шаблонах обработчиков. Включить проверку идемпотентности в code review checklist. Рассмотреть хранение `InboxMessageId` в таблицах-потребителях для дедупликации.

2. **Задержка доставки при сбое фонового процесса**  
   Если фоновый процесс Wolverine недоступен (сбой пода, перезапуск), сообщения накапливаются в outbox и не доставляются до восстановления процесса.  
   *Меры:* Настроить алерт на метрику `wolverine_outgoing_envelopes_total{status="outstanding"}` (порог — 100 сообщений, задержка — 5 минут). Обеспечить быстрый рестарт подов через readiness/liveness probes в Kubernetes.

3. **Отсутствие миграций для таблицы outbox**  
   Если сервис не применил EF Core миграции для создания `wolverine_outgoing_envelopes`, `SaveChangesAsync` будет падать в runtime.  
   *Меры:* Добавить smoke-тест при старте приложения, проверяющий наличие outbox-таблицы. Включить применение миграций в CI/CD pipeline как обязательный шаг перед деплоем.

4. **Рост таблицы outbox при недоступности брокера**  
   При длительной недоступности Kafka или RabbitMQ таблица `wolverine_outgoing_envelopes` будет расти, что может повлиять на производительность БД.  
   *Меры:* Настроить мониторинг размера таблицы. Определить TTL для сообщений в DLQ. Проверить, что Wolverine корректно очищает доставленные записи (подтвердить конфигурацию purge-политики).

5. **Известный баг Requeue в Kafka-транспорте**  
   Политика Requeue некорректно работает с Kafka: сообщения могут быть потеряны при повторной постановке в очередь (унаследовано из ADR-006).  
   *Меры:* Запретить политику Requeue для всех Kafka-обработчиков через code review checklist. Всегда использовать `MoveToDeadLetterQueue()`. Периодически проверять статус бага в новых версиях Wolverine.
