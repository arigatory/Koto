# ADR-014: Quartz.NET для распределённого планирования задач в Koto.Scheduling

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

Микросервисы в Koto-стеке нуждаются в механизме запуска периодических и пакетных задач (scheduled/batch jobs): например, ежедневное формирование отчётов, периодическая очистка устаревших данных, агрегация метрик.

Критическое ограничение: Kubernetes HPA (Horizontal Pod Autoscaler) может горизонтально масштабировать сервис до нескольких подов. Наивный подход — `BackgroundService` с таймером — запускает задачу в **каждом** поде одновременно:

```csharp
// BackgroundService + Timer — запускается в КАЖДОМ поде:
protected override async Task ExecuteAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        await DoJobAsync(ct);        // выполнится 3 раза, если запущено 3 пода!
        await Task.Delay(TimeSpan.FromHours(1), ct);
    }
}
```

Это приводит к дублированию работы, конфликтам при записи данных, некорректной статистике и потенциально к ошибкам при параллельной модификации одних и тех же ресурсов.

Требуется решение, которое гарантирует выполнение каждой задачи **ровно один раз** вне зависимости от количества запущенных подов.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Единственное выполнение | Каждая задача должна запускаться ровно один раз при любом количестве подов (distributed locking) |
| Cron-расписание | Поддержка стандартных cron-выражений для задания периодичности |
| Восстановление после сбоя | Если под перезапустился в момент выполнения задачи, задача должна быть восстановлена и повторно выполнена |
| История выполнений | Хранение истории запусков: время начала, завершения, результат, ошибки |
| Программная регистрация | Задачи регистрируются через DI-контейнер, без XML-конфигурации |
| Интеграция с PostgreSQL | Хранение состояния планировщика в уже используемой PostgreSQL-базе |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Лицензия | MIT или совместимая с коммерческим использованием | Обязательно |
| Зрелость | Библиотека должна быть зрелой, с активным сообществом и долгой историей | Высокая |
| .NET 10+ | Первоклассная поддержка .NET 10 и выше | Обязательно |
| Минимальный бойлерплейт | Регистрация задач через fluent API; интеграция с `IServiceProvider` | Высокая |
| Изоляция зависимости | Зависимость на планировщик изолирована в `Koto.Scheduling`; бизнес-логика не знает о Quartz | Обязательно |
| Мониторинг | Возможность наблюдать за состоянием задач и их историей | Средняя |

---

## 3. Решение

### Описание

**Quartz.NET** выбран как стандартный планировщик задач для всех Koto-микросервисов, нуждающихся в периодическом или пакетном выполнении.

Quartz.NET в кластерном режиме использует **PostgreSQL как распределённую блокировку**: когда несколько подов запускают один и тот же триггер, PostgreSQL-транзакция гарантирует, что только один под «выигрывает» блокировку и выполняет задачу. Остальные поды пропускают этот запуск.

Koto предоставляет пакет `Koto.Scheduling`, который скрывает детали конфигурации Quartz и предоставляет простой API регистрации:

```csharp
// Регистрация в Program.cs:
services.AddKotoScheduling(quartz =>
{
    // Quartz хранит состояние задач в PostgreSQL → только один под получает блокировку
    quartz.UsePersistentStore(store =>
    {
        store.UsePostgres(connectionString);
        store.UseSystemTextJsonSerializer();
        store.UseClustering();
    });

    quartz.AddJob<DailyReportJob>(cron: "0 0 8 * * ?");
    quartz.AddJob<CleanupJob>(cron: "0 */15 * * * ?");
});
```

Задачи реализуют интерфейс `IJob` из Quartz, но Koto предоставляет базовый класс `KotoJob`, интегрированный с `ICqrsDispatcher`, чтобы задача могла диспетчеризировать команды так же, как HTTP-эндпоинт:

```csharp
// Задача реализует бизнес-логику через команду — никаких прямых зависимостей на Quartz в логике
public class DailyReportJob : KotoJob
{
    public override async Task ExecuteAsync(IJobExecutionContext context, CancellationToken ct)
    {
        await Dispatcher.SendAsync(new GenerateDailyReportCommand(DateOnly.FromDateTime(DateTime.UtcNow)), ct);
    }
}
```

Для разовых пакетных задач, не привязанных к внутреннему расписанию сервиса, рекомендован паттерн **K8s CronJob**: Kubernetes управляет жизненным циклом пода, повторными попытками и параллелизмом. Оба подхода задокументированы в примере `DataPipeline`.

### Аргументация

| Критерий | Обоснование |
|---|---|
| Распределённая блокировка | Кластерный режим Quartz.NET с PostgreSQL гарантирует единственное выполнение задачи при любом масштабировании — это закрывает ключевую проблему |
| Зрелость и надёжность | Quartz.NET — порт Java-библиотеки Quartz (2007), активно поддерживается с 2004 г., 6k+ звёзд на GitHub, широко применяется в продакшне |
| MIT-лицензия | Нет коммерческих ограничений, в отличие от Hangfire Pro |
| .NET 10+ first-class | Официальная поддержка, интеграция с `Microsoft.Extensions.Hosting`, DI, `IHostedService` |
| Cron-выражения | Стандартный формат, знакомый разработчикам; богатая семантика (секунды, кварталы, etc.) |
| Восстановление задач | `[DisallowConcurrentExecution]` и `[PersistJobDataAfterExecution]` позволяют корректно обработать сбои и перезапуски |
| Мониторинг | История выполнений хранится в БД; совместим с OpenTelemetry и сторонними дашбордами |

#### Последствия

**Положительные:**
- Задачи гарантированно выполняются ровно один раз при любом количестве подов — решает ключевую проблему масштабирования
- Бизнес-логика задач изолирована в хендлерах команд; `KotoJob` — тонкая обёртка-адаптер
- PostgreSQL уже присутствует в стеке (Marten, ADR-007) — отдельной инфраструктуры не требуется
- Восстановление после сбоя из коробки — не нужно реализовывать idempotency вручную для периодических задач
- Единая точка мониторинга: история, время выполнения, сбои — всё в одном месте

**Негативные:**
- Quartz.NET добавляет зависимость на PostgreSQL-схему (11 системных таблиц); миграции нужно учитывать при деплое
- Кластерный режим требует точной синхронизации часов между подами (рекомендован NTP/PTP в K8s)
- Тестирование задач требует либо поднятия PostgreSQL (интеграционные тесты), либо мокирования `IScheduler`
- Quartz.NET сложнее в конфигурации, чем простой `BackgroundService`, — новичкам нужно время на освоение

**Зависимости:**
- `Koto.Scheduling` (новый пакет) оборачивает `Quartz.NET` и `Quartz.Extensions.Hosting`; предоставляет `AddKotoScheduling()` и базовый класс `KotoJob`
- `Koto.Scheduling` зависит от `Koto.Application` для доступа к `ICqrsDispatcher`
- Микросервисы, использующие периодические задачи, берут зависимость только на `Koto.Scheduling`; прямая зависимость на Quartz не нужна
- PostgreSQL-схема Quartz инициализируется автоматически при старте через `UseJobStoreClustered` с `TablePrefix`

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **BackgroundService + Timer** | Встроено в .NET; нулевые зависимости; прост в понимании | Нет распределённой блокировки — задача запускается в каждом поде; нет восстановления после сбоя; нет истории | Напрямую нарушает ключевое требование единственного выполнения при масштабировании |
| **Hangfire** (свободная версия) | Популярен; богатый UI-дашборд; хорошая документация | Свободная версия ограничена: нет распределённых очередей, нет приоритетов; Pro — коммерческий; менее подходит для микросервисной архитектуры | Лицензионные ограничения неприемлемы; Quartz.NET предоставляет аналогичный функционал бесплатно |
| **K8s CronJob** | K8s управляет жизненным циклом, повторами, параллелизмом; не требует библиотечной зависимости | Каждая задача — отдельный контейнер/деплоймент; неудобно для задач, плотно интегрированных с бизнес-логикой сервиса; ограниченная гранулярность расписания | Рекомендован как дополнение для разовых batch-задач, но не замена для внутрипроцессного cron |
| **Wolverine Scheduling** | Уже присутствует в стеке (ADR-006); единая модель для сообщений и расписания | Планировщик в Wolverine менее зрелый, чем Quartz; ориентирован на отложенную отправку сообщений, а не на cron-расписание | Не покрывает сценарии cron-задач так же полно, как Quartz.NET; может дополнять, но не заменять |
| **Azure Functions / AWS Lambda** | Managed-сервис; масштабирование из коробки; богатые триггеры | Привязка к облачному провайдеру; нет переносимости; накладные расходы на холодный старт | Противоречит принципу переносимости Koto-стека; не подходит для on-premise и мультиоблачных сценариев |

### 5. Риски

1. **Дрейф часов между подами нарушает кластерный режим**  
   *Меры:* Документировать требование к NTP-синхронизации в CONTRIBUTING.md. В Helm-чарте настроить `hostPID: true` и синхронизацию с node-clock. Добавить метрику-алерт на расхождение системного времени подов более чем на 1 секунду.

2. **Схема Quartz конфликтует с миграциями Marten или приложения**  
   *Меры:* Использовать выделенный `TablePrefix` для Quartz (например, `QRTZ_`) и отдельную схему PostgreSQL (`scheduling`). Инициализация схемы выполняется автоматически при старте через `UseJobStoreClustered` — не через Flyway/EF-миграции.

3. **Тестирование задач в изолированной среде**  
   *Меры:* `KotoJob` полностью тестируем через мокирование `ICqrsDispatcher`. Интеграционные тесты с реальным Quartz используют Testcontainers с PostgreSQL. Шаблоны тестов добавить в `Koto.Testing`.

4. **Зависимость от Quartz.NET — смена лицензии или заброшенность**  
   *Меры:* Зависимость инкапсулирована в `Koto.Scheduling`; бизнес-логика задач взаимодействует только с `KotoJob` и `ICqrsDispatcher`. При необходимости замены планировщика достаточно изменить `Koto.Scheduling`, не трогая хендлеры. Мониторить репозиторий Quartz.NET.

5. **Рост числа задач перегружает одну PostgreSQL-таблицу**  
   *Меры:* Quartz.NET хранит только актуальные триггеры; история выполнений не накапливается бесконечно. При необходимости долгосрочного хранения истории — экспорт в отдельную таблицу через `IJobListener`. При очень высокой нагрузке рассмотреть выделенную БД для Quartz.
