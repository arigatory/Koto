# ADR-001: Koto.Domain не имеет внешних NuGet-зависимостей

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

`Koto.Domain` — это фундаментальный пакет всего Koto-стека. Он содержит базовые строительные блоки предметной области:
`Entity`, `AggregateRoot`, `ValueObject`, `Result<T, Error>`, `Error`, `IDomainEvent`, `IRepository`.

Поскольку `Koto.Domain` является **транзитивной зависимостью** всех остальных Koto-пакетов, любая внешняя зависимость, добавленная на этом уровне, автоматически распространяется на каждый потребляющий проект, каждый микросервис и каждый пакет в экосистеме Koto.

При проектировании пакета был рассмотрен популярный NuGet-пакет **CSharpFunctionalExtensions** (лицензия MIT, ~2 800 звёзд на GitHub), разработанный Владимиром Хориковым — автором книги «Принципы юнит-тестирования». Библиотека предоставляет готовые реализации `Result<T, Error>`, `Maybe<T>` и `ValueObject`, хорошо спроектирована и пользуется широким уважением в сообществе.

Тем не менее от её использования было решено отказаться. Данный ADR фиксирует принятое решение, его обоснование и рассмотренные альтернативы.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Строительные блоки DDD | Пакет должен предоставлять `Entity<TId>`, `AggregateRoot<TId>`, `ValueObject` как абстрактные базовые типы |
| Результат операции | Пакет должен предоставлять `Result<T, Error>` для явного представления успеха или провала без исключений |
| Ошибки | Пакет должен предоставлять тип `Error` с кодом, сообщением и опциональными метаданными, адаптированный под нужды Koto |
| Доменные события | Пакет должен предоставлять интерфейс `IDomainEvent` |
| Репозитории | Пакет должен предоставлять обобщённый интерфейс `IRepository<TAggregate, TId>` |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Независимость | Пакет не должен ссылаться ни на один внешний NuGet-пакет | Обязательно |
| Размер | Вся реализация должна укладываться в ~400 строк кода и оставаться понятной без дополнительной документации | Высокая |
| Стабильность API | Публичный API пакета должен находиться под полным контролем команды Koto | Обязательно |
| Переносимость лицензии | Лицензионные условия пакета не должны зависеть от решений сторонних разработчиков | Высокая |
| Прозрачность | Каждый потребитель Koto должен иметь возможность прочитать и понять всю реализацию | Средняя |

---

## 3. Решение

### Описание

**`Koto.Domain` реализуется полностью на чистом C# без каких-либо внешних NuGet-зависимостей.**

Все типы пишутся с нуля и остаются частью пакета. Файл проекта `Koto.Domain.csproj` содержит только секцию `<PropertyGroup>` — без единого элемента `<PackageReference>`.

```xml
<!-- Koto.Domain.csproj — намеренно без <PackageReference> -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
```

Ключевые типы, реализуемые в пакете:

```csharp
// Result<T, Error> — полностью под нашим контролем.
// Мы сами управляем API: именованием методов, поведением при матчинге,
// интеграцией с нашим типом Error.
public sealed class Result<T, TError>
{
    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public T Value { get; }       // выбрасывает, если IsFailure
    public TError Error { get; }   // выбрасывает, если IsSuccess

    private Result(T value) { /* ... */ }
    private Result(TError error) { /* ... */ }

    public static Result<T, TError> Success(T value) => new(value);
    public static Result<T, TError> Failure(TError error) => new(error);

    public TOut Match<TOut>(Func<T, TOut> onSuccess, Func<TError, TOut> onFailure)
        => IsSuccess ? onSuccess(Value) : onFailure(Error);
}

// Error — специфичен для Koto; содержит структурированный код,
// понятное сообщение и опциональные метаданные.
// Ни одна сторонняя библиотека не навязывает нам эту форму.
public sealed record Error(string Code, string Message)
{
    public static readonly Error None = new(string.Empty, string.Empty);

    public static Error NotFound(string resource, object id)
        => new($"{resource}.NotFound", $"{resource} with id '{id}' was not found.");

    public static Error Validation(string field, string message)
        => new($"Validation.{field}", message);
}

// ValueObject — структурное равенство по значению без зависимости
// от CSharpFunctionalExtensions.ValueObject.
public abstract class ValueObject
{
    protected abstract IEnumerable<object?> GetEqualityComponents();

    public override bool Equals(object? obj)
    {
        if (obj is null || obj.GetType() != GetType()) return false;
        return GetEqualityComponents()
            .SequenceEqual(((ValueObject)obj).GetEqualityComponents());
    }

    public override int GetHashCode()
        => GetEqualityComponents()
            .Aggregate(0, HashCode.Combine);
}
```

Для сравнения — то, от чего `Koto.Domain` **намеренно отказывается**:

```csharp
// НЕ используется: CSharpFunctionalExtensions
// using CSharpFunctionalExtensions;
//
// public class Order : AggregateRoot<OrderId>  // ← тип из сторонней библиотеки
// public Result<Order, Error> Place(...) { ... } // ← Result из сторонней библиотеки
// public Maybe<Customer> FindCustomer(...) { } // ← Maybe из сторонней библиотеки
//
// Любое изменение версии CSharpFunctionalExtensions ломает весь Koto-стек.
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Транзитивное распространение | `Koto.Domain` — это транзитивная зависимость каждого Koto-пакета. Один внешний пакет здесь превращается во внешний пакет везде: в микросервисах, в библиотеках, у конечных пользователей |
| Риск изменения API | Мажорные обновления сторонних библиотек могут изменить сигнатуры методов и привести к каскадным компиляционным ошибкам по всему стеку |
| Риск смены лицензии | В 2024–2025 гг. MediatR, MassTransit и FluentValidation сменили условия лицензирования. Зависимость от сторонней библиотеки означает, что судьба лицензии Koto частично в чужих руках |
| Небольшой объём реализации | Весь необходимый код — около 400 строк. Это не та задача, ради которой стоит вводить внешнюю зависимость |
| Интернализованные знания | Команда глубоко изучила паттерны из книги Хорикова. Знание уже усвоено — брать готовую реализацию ради экономии 400 строк нет смысла |
| Контроль над API | Собственная реализация позволяет точно подогнать API под нужды Koto: например, специфичный дизайн типа `Error` с кодом и метаданными |

#### Последствия

**✅ Положительные:**
- Нулевой транзитивный риск для всех потребителей Koto: никаких неожиданных зависимостей в их графе пакетов
- Полный контроль над API, семантикой и эволюцией базовых типов
- Отсутствие зависимости от сторонних решений по лицензированию и версионированию
- Каждый разработчик может прочитать и понять всю реализацию в рамках одного пакета
- Упрощённый граф зависимостей упрощает аудит безопасности и анализ цепочки поставок (supply chain)

**⚠️ Негативные:**
- Команда несёт полную ответственность за сопровождение `Result<T, Error>`, `ValueObject` и сопутствующих типов
- Новые участники не могут опереться на документацию или обсуждения сообщества по CSharpFunctionalExtensions — нужно читать наш код
- Улучшения сторонних библиотек не достаются нам автоматически; их придётся портировать вручную при необходимости

**↗️ Зависимости:**
- Все пакеты Koto (`Koto.Application`, `Koto.Infrastructure`, `Koto.Persistence` и т. д.) зависят от `Koto.Domain`, поэтому данное решение затрагивает весь стек
- Потребляющие проекты получают гарантию: `Koto.Domain` никогда не добавит транзитивный «груз» в их сборку
- Будущие решения об изменении API `Result<T, Error>` или `Error` также подчиняются настоящему ADR и принимаются командой Koto единолично

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **CSharpFunctionalExtensions** (Хориков) | Хорошо спроектирован, проверен сообществом, содержит `Result<T, Error>`, `Maybe<T>`, `ValueObject` | Транзитивная зависимость во всём стеке; риск смены лицензии (прецеденты 2024–2025 гг.); API не всегда соответствует нашему дизайну `Error` | Риск транзитивного распространения неприемлем для фундаментального пакета; объём кода, который нужно взять из библиотеки, слишком мал, чтобы оправдать зависимость |
| **ErrorOr** | Лаконичный API; удобен для минималистичных сценариев обработки ошибок | Иная философия (список ошибок вместо единственной); структура `Error` не совпадает с нашим дизайном; тот же транзитивный риск | Концептуально не вписывается в подход Koto; не решает проблему транзитивной зависимости |
| **OneOf** | Истинные типы-объединения в C#; выразительный синтаксис для дискриминированных объединений | Паттерн Union Types избыточен там, где достаточен Result; крутая кривая обучения для потребителей; тот же транзитивный риск | Чрезмерно сложен для задачи «успех или провал»; несовместим с нашей моделью `Error`; не решает транзитивный риск |

---

### 5. Риски

1. **Дивергенция с лучшими практиками сообщества**  
   *Меры:* Периодически просматривать CHANGELOG CSharpFunctionalExtensions и аналогичных библиотек на предмет улучшений; при необходимости адаптировать идеи, не беря зависимость. Рассмотреть внутренние ревью API раз в полгода.

2. **Ошибки в самописной реализации Result<T, Error> или ValueObject**  
   *Меры:* Покрыть базовые типы исчерпывающими юнит-тестами (включая граничные случаи равенства, поведение при `null`, корректность `GetHashCode`). Тесты входят в `Koto.Domain.Tests` и выполняются в CI при каждом пуше.

3. **Давление со стороны новых участников с просьбой «просто добавить» стороннюю библиотеку**  
   *Меры:* Настоящий ADR служит зафиксированным обоснованием решения. Ссылаться на него в ревью PR и в документации для контрибьюторов. Указывать на него в CONTRIBUTING.md.

4. **Увеличение объёма поддержки при росте стека**  
   *Меры:* Удерживать `Koto.Domain` намеренно небольшим и стабильным. Не добавлять в него удобные утилиты — только фундаментальные абстракции DDD. Любые дополнения требуют отдельного ADR.
