# ADR-018: DDD-ориентированные тест-хелперы в Koto.Testing

**Статус:** ✅ Принято  
**Дата:** 2026-06-29  

---

## 1. Контекст

Юнит-тесты доменной модели в DDD-сервисе повторяют один и тот же ритуал: построить агрегат в нужном состоянии, выполнить бизнес-операцию, проверить результат (`Result<T>`) и поднятые доменные события. Без общих хелперов каждый сервис заново пишет:
- сборку агрегата из прошлых событий (для сценариев «дано»);
- проверки на то, что операция подняла ожидаемое доменное событие;
- in-memory заглушки `IRepository` и `IIntegrationEventPublisher`;
- ассерты на `Result<T>` (успех/провал, конкретный код ошибки).

Это приводит к разнобою стилей тестов между сервисами и к копированию фейков. Требуется небольшой пакет тест-хелперов, специфичных именно для строительных блоков Koto (`AggregateRoot<TId>`, `IDomainEvent`, `Result<T>`, `IRepository`, `IIntegrationEventPublisher`).

Отдельно: в `Koto.Testing.Architecture` (см. [ADR-015](ADR-015-archunit-fitness-functions.md)) решается **другая** задача — архитектурные fitness-функции через ArchUnitNET. Настоящий ADR описывает `Koto.Testing` — хелперы для **юнит-тестов домена**, не путать с ним.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Given/When/Then | Fluent-фикстура для тестов агрегата: задать начальное состояние, выполнить операцию, проверить исход |
| Проверка событий | Ассерты на поднятые доменные события: тип, содержимое, точное количество |
| Реконструкция состояния | Возможность восстановить состояние агрегата из прошлых событий в секции «дано» |
| In-memory фейки | Заглушки `IRepository<TAgg,TId>` и `IIntegrationEventPublisher` для тестов сценариев |
| Ассерты Result | Расширения проверки `Result<T>`: успех, провал, провал с конкретным кодом, значение |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Лицензия | Только MIT/Apache 2.0; никаких коммерческих зависимостей в тест-стеке | Обязательно |
| Знакомый DX | Синтаксис ассертов в стиле FluentAssertions, привычный команде | Высокая |
| Фреймворк-нейтральность к раннеру | Работает с xUnit (основной раннер стека), не завязан жёстко на конкретные атрибуты | Средняя |
| Минимум зависимостей | Зависит только от `Koto.Domain`, `Koto.Application` и библиотеки ассертов | Высокая |
| Опциональность | Пакет необязателен: домен тестируется и без него, хелперы лишь убирают бойлерплейт | Средняя |

---

## 3. Решение

### Описание

**Koto.Testing** предоставляет тонкий набор DDD-хелперов поверх **AwesomeAssertions** (MIT-форк FluentAssertions — выбран потому, что FluentAssertions v8 ушёл в коммерцию, см. раздел «Лицензионные ловушки» в CLAUDE.md и [ADR-009](ADR-009-fluent-validation-must-be-value-object.md)).

Ключевые типы:

| Тип | Назначение |
|---|---|
| `AggregateTestFixture<TAgg>` | Fluent Given/When/Then для юнит-тестов агрегата |
| `AggregateAssertions<TAgg>` | Ассерты на поднятые доменные события |
| `FakeRepository<TAgg, TId>` | In-memory реализация `IRepository<TAgg,TId>` |
| `FakeIntegrationEventPublisher` | Перехватывает опубликованные `IIntegrationEvent` |
| `ResultAssertions<T>` | `.Should().BeSuccess()`, `.BeFailure()`, `.BeFailureWith("code")`, `.HaveValue(x)` |
| `IAggregateApply<TEvent>` | Опциональный интерфейс агрегата для реконструкции состояния в `Given()` |

Тест агрегата читается как спецификация поведения:

```csharp
[Fact]
public void Cancel_raises_OrderCancelled_event()
{
    new AggregateTestFixture<Order>()
        .Given(new OrderPlaced(orderId, customerId))
        .When(o => o.Cancel("Customer request"))
        .Then()
        .ShouldHaveRaisedEvent<OrderCancelled>(e => e.Reason == "Customer request")
        .And.ShouldHaveRaisedExactly(1);
}
```

Ассерты на `Result<T>` и фейки инфраструктуры:

```csharp
var result = order.Cancel("reason");
result.Should().BeSuccess();
result.Should().BeFailureWith("orders.order.already-cancelled");

var repo = new FakeRepository<Order, OrderId>();
var publisher = new FakeIntegrationEventPublisher();
// ... выполнить use case ...
repo.All.Should().ContainSingle();
publisher.GetPublishedEvent<OrderPlacedEvent>().OrderId.Should().Be(orderId);
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Убирает бойлерплейт | Сборка агрегата, проверка событий, фейки и ассерты `Result` — один раз в пакете, а не в каждом сервисе |
| Единый стиль тестов | Given/When/Then делает доменные тесты читаемыми как спецификации поведения |
| Доменная семантика | Ассерты говорят на языке домена (события, `Result`, коды ошибок), а не на языке общих моков |
| AwesomeAssertions | MIT-форк с тем же API, что у привычного FluentAssertions; нет коммерческих рисков |
| Опциональность | Пакет не навязан: тесты домена возможны и без него — `Koto.Testing` лишь повышает эргономику |

#### Последствия

**Положительные:**
- Доменные тесты единообразны по всему стеку и читаются как поведенческие спецификации
- In-memory фейки убирают необходимость поднимать инфраструктуру для проверки сценариев use-case
- Ассерты `Result<T>` фиксируют контракт ошибок (коды) явно в тесте
- Реконструкция через `IAggregateApply<TEvent>` позволяет писать event-sourcing-style тесты «дано прошлые события»

**Негативные:**
- Хелперы связаны с базовыми типами Koto (`AggregateRoot<TId>`, `IDomainEvent`, `Result<T>`) — это сознательная привязка к стеку
- `AggregateTestFixture` подходит для модульных тестов агрегата; интеграционные сценарии (БД, Kafka) тестируются отдельно через Testcontainers
- Риск разрастания пакета удобными, но узкоспециальными хелперами

**Зависимости:**
- `Koto.Testing` зависит от `Koto.Domain` и `Koto.Application` (доступ к `IRepository`, `IIntegrationEventPublisher`)
- Зависимость на `AwesomeAssertions` (MIT)
- Интеграционные тесты инфраструктуры используют Testcontainers + PostgreSQL и не входят в этот пакет

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Самописные фейки в каждом сервисе** | Полная свобода под нужды сервиса | Дублирование фейков и ассертов; разнобой стилей между сервисами | Ровно та проблема, которую централизует пакет |
| **Только общий мокинг (NSubstitute)** | Гибко, уже в тест-стеке | Моки не несут доменной семантики (события, `Result`, коды); тесты многословны | Не даёт выразительности Given/When/Then и доменных ассертов |
| **FluentAssertions напрямую** | Богатый API ассертов | v8+ коммерческий (Xceed); нет доменных расширений под `Result`/события | Лицензионный риск; нет DDD-специфики — закрыто связкой AwesomeAssertions + хелперы Koto |
| **Полноценный BDD-фреймворк (SpecFlow/Reqnroll)** | Сценарии на естественном языке | Тяжёлый инструмент; избыточен для юнит-тестов агрегата | Несоразмерно задаче; усложняет онбординг ради юнит-тестов домена |

---

### 5. Риски

1. **Привязка тест-хелперов к базовым типам Koto усложняет их эволюцию**  
   *Меры:* Держать API пакета минимальным и стабильным; изменения базовых типов (`AggregateRoot`, `Result`) сопровождать обновлением хелперов в том же релизе.

2. **Смена лицензии AwesomeAssertions**  
   *Меры:* AwesomeAssertions — MIT-форк; API совместим с FluentAssertions, поэтому при необходимости миграция предсказуема. Мониторить статус форка.

3. **Разрастание пакета узкоспециальными хелперами**  
   *Меры:* Новый хелпер добавляется только при наличии нескольких реальных use-case; границы пакета фиксируются в README; размытие ответственности требует нового ADR.

4. **Подмена интеграционных тестов модульными из-за удобства фейков**  
   *Меры:* Чётко разграничить в документации: `FakeRepository` — для логики use-case; реальное поведение БД/Kafka проверяется интеграционными тестами на Testcontainers.
