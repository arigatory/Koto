# ADR-017: Serilog + OpenTelemetry для наблюдаемости в Koto.Observability

**Статус:** ✅ Принято  
**Дата:** 2026-06-29  

---

## 1. Контекст

Микросервисы Koto-стека работают в распределённой среде (Kubernetes, несколько подов, асинхронные сообщения через Kafka). Без сквозной наблюдаемости (логи, трейсы, метрики) диагностика инцидентов в такой среде практически невозможна: запрос проходит через несколько сервисов, и нужно видеть единую картину.

Требуется решение, которое:
- даёт **структурированные логи**, трассировку и метрики «из коробки», без копирования бойлерплейта в каждый сервис;
- не привязывает Koto к конкретному вендору наблюдаемости (Datadog, Application Insights, New Relic);
- связывает логи и трейсы единым `CorrelationId`, который уже пробрасывается через `Koto.Api.FastEndpoints` и `Koto.Messaging.Wolverine`.

Наивный подход — настраивать Serilog и OpenTelemetry вручную в каждом `Program.cs` — приводит к расхождению конфигураций между сервисами и дублированию десятков строк.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Структурные логи | Логи в структурированном формате с обогащением (сервис, окружение, `CorrelationId`) |
| Трассировка | Распределённые трейсы для входящих HTTP-запросов и исходящих `HttpClient`-вызовов |
| Метрики | Метрики ASP.NET Core (запросы, латентность) и .NET Runtime (GC, пулы потоков) |
| Корреляция | Единый `CorrelationId` в каждом логе и трейсе для сшивки запроса между сервисами |
| Однострочная настройка | Вся обвязка включается одним вызовом `AddKotoObservability()` |
| Конфигурация через ENV | Endpoint, имя сервиса и уровень логирования читаются из стандартных переменных окружения |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Вендор-нейтральность | Экспорт по открытому протоколу **OTLP**; никакой привязки к конкретному backend | Обязательно |
| Лицензия | MIT / Apache 2.0 для всех зависимостей | Обязательно |
| Изоляция зависимости | Детали Serilog/OTel скрыты за `Koto.Observability`; бизнес-логика их не знает | Высокая |
| Совместимость с дев-средой | В разработке — человекочитаемый console-вывод; в проде — OTLP | Средняя |
| Минимальный оверхед | Инструментирование не должно заметно влиять на латентность горячего пути | Высокая |

---

## 3. Решение

### Описание

**Koto.Observability** объединяет два зрелых стандарта: **Serilog** для логов и **OpenTelemetry .NET** для трейсов и метрик. Экспорт идёт по **OTLP** в любой совместимый коллектор (OpenTelemetry Collector, Grafana Alloy, Jaeger, Tempo, Prometheus и т. д.) — Koto не знает и не диктует, какой backend стоит за коллектором.

Вся настройка — один вызов на `HostApplicationBuilder`:

```csharp
// Program.cs
builder.AddKotoObservability(opts =>
{
    opts.ServiceName = "orders-service";
    opts.EnableConsoleExporter = true; // только для разработки
    // связать CorrelationId с HTTP-middleware из Koto.Api.FastEndpoints
    opts.CorrelationIdProvider = () => CorrelationContext.Current.Value;
});
```

Состав:
- **Serilog** — структурные логи, console-sink (dev) + OTLP-sink (prod), enrichers (окружение + `CorrelationIdEnricher`).
- **OpenTelemetry Traces** — инструментирование ASP.NET Core и `HttpClient` → OTLP.
- **OpenTelemetry Metrics** — ASP.NET Core + .NET Runtime → OTLP.
- `ObservabilityOptions` — `ServiceName`, `OtlpEndpoint`, `MinimumLevel`, `CorrelationIdProvider`, `EnableConsoleExporter`.

Значения по умолчанию берутся из стандартных переменных окружения:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `OTEL_SERVICE_NAME` | `"unknown-service"` | Имя сервиса в ресурсе OTel |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `"http://localhost:4317"` | Endpoint OTLP-коллектора |
| `KOTO_LOG_LEVEL` | `"Information"` | Минимальный уровень логирования Serilog |

### Аргументация

| Критерий | Обоснование |
|---|---|
| Вендор-нейтральность | OTLP — открытый стандарт CNCF; backend заменяется без изменения кода сервисов |
| Зрелость | Serilog — де-факто стандарт структурного логирования в .NET; OpenTelemetry — отраслевой стандарт телеметрии |
| Единый CorrelationId | Логи и трейсы сшиваются по одному идентификатору, который уже генерируется в API- и messaging-слоях Koto |
| Однострочная настройка | `AddKotoObservability()` устраняет расхождение конфигураций между сервисами |
| Дружелюбность к dev | Console-exporter включается флагом; в проде — только OTLP |
| Лицензии | Serilog (Apache 2.0) и OpenTelemetry .NET (Apache 2.0) — без коммерческих ограничений |

#### Последствия

**Положительные:**
- Любой Koto-сервис получает логи, трейсы и метрики одним вызовом — единообразно по всему стеку
- Полная свобода выбора backend наблюдаемости (Grafana-стек, Jaeger, коммерческие APM с OTLP-приёмом)
- `CorrelationId` сшивает картину запроса, проходящего через несколько сервисов и Kafka
- Детали телеметрии изолированы в `Koto.Observability` — обновление версий не затрагивает бизнес-код

**Негативные:**
- Набор пакетов OpenTelemetry .NET активно эволюционирует — периодически требуется синхронный апгрейд версий
- Инструментирование добавляет небольшой оверхед на горячем пути (приемлемо при разумной частоте сэмплирования)
- Требуется развёрнутый OTLP-коллектор в инфраструктуре — это операционная зависимость

**Зависимости:**
- `Koto.Observability` зависит от `Serilog.AspNetCore`, `Serilog.Sinks.OpenTelemetry`, `Serilog.Enrichers.Environment` и пакетов `OpenTelemetry.*` (Hosting, Instrumentation.AspNetCore/Http/Runtime, Exporter.OpenTelemetryProtocol)
- `CorrelationIdProvider` опционально связывается с `CorrelationContext` из `Koto.Api.FastEndpoints`
- Инструментирование EF Core (`OpenTelemetry.Instrumentation.EntityFrameworkCore`) пока без стабильного релиза — добавляется вручную после выхода

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Только `Microsoft.Extensions.Logging`** | Встроено в .NET; ноль зависимостей | Нет структурного обогащения уровня Serilog; нет трейсов и метрик; нет OTLP | Не покрывает трассировку и метрики — лишь часть задачи наблюдаемости |
| **Application Insights SDK** | Богатый UI; глубокая интеграция с Azure | Привязка к вендору (Azure); проприетарный протокол; плохая переносимость | Противоречит принципу вендор-нейтральности и переносимости Koto |
| **Ручная настройка Serilog + OTel в каждом сервисе** | Максимальная гибкость на местах | Десятки строк бойлерплейта; конфигурации расходятся между сервисами | Дублирование и дрейф конфигураций — ровно та проблема, которую решает пакет |
| **Чистый OpenTelemetry Logs (без Serilog)** | Единый стек OTel для всех сигналов | OTel Logs для .NET менее зрел; экосистема enrichers/sinks беднее, чем у Serilog | Serilog даёт более зрелый DX для логов; OTLP-sink Serilog закрывает экспорт |

### 5. Риски

1. **Рассинхрон версий пакетов OpenTelemetry**  
   *Меры:* Зафиксировать версии `OpenTelemetry.*` в `Directory.Packages.props`/csproj; обновлять их одним согласованным PR; покрывать smoke-тестом, что сервис стартует и экспортирует телеметрию.

2. **Неверно сконфигурированный OTLP endpoint молча теряет телеметрию**  
   *Меры:* Логировать на старте фактический `OtlpEndpoint` и `ServiceName`; в dev включать console-exporter для визуальной проверки; добавить health-check доступности коллектора.

3. **Оверхед инструментирования на горячем пути**  
   *Меры:* Использовать разумный sampling для трейсов в проде; не логировать на уровне Debug в продакшне (`KOTO_LOG_LEVEL`); периодически профилировать латентность.

4. **Утечка чувствительных данных в логи/трейсы**  
   *Меры:* Не логировать тела запросов и PII по умолчанию; задокументировать правила маскирования; ревью атрибутов трейсов на отсутствие секретов.

5. **Смена лицензии или заброшенность зависимости телеметрии**  
   *Меры:* Зависимости изолированы в `Koto.Observability`; при необходимости замены достаточно изменить один пакет, не трогая сервисы. Мониторить статус Serilog и OpenTelemetry .NET.
