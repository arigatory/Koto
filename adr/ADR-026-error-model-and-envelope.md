# ADR-026: Модель ошибок v0.5 — каталог record-типов, EnrichedError, AppResult и конверт ответа

**Статус:** ✅ Принято  
**Дата:** 2026-11-08  
**Заменяет:** ADR-020 (ProblemDetails). **Ревизует:** ADR-002 (Result), ADR-003 (Error).

---

## 1. Контекст

Ревизия ядра на двух потребителях (Real Board Games, agent-server) показала четыре связанные проблемы.

1. **Проброс терял ошибки.** С v0.3 `Result<T>` мульти-ошибочный, но единственный короткий способ пробросить
   отказ — `return x.Error;` — возвращал первую из N. В потребителях ≈85 таких мест и ни одного
   `Failure(x.Errors)`. Библиотека давала `Combine`/`Traverse`, чтобы собрать все ошибки, и делала их выброс
   самым коротким кодом.
2. **Три формы ошибки в одном сервисе.** Одиночная (`detail` + `errorCode`), множественная
   (`errors: {поле: [тексты]}` + `errorCodes`), ошибки биндинга FastEndpoints (`ErrorResponse`). Клиенты
   угадывали: landing koto-agent разбирал две формы и склеивал тексты; мобильный клиент RBG читал
   несуществующие поля `code` и `errors[0].code`.
3. **Фронту нужны данные, а не только текст.** Перезапустить таймер по `retryAfterSeconds`, перезагрузить
   версию по `actualVersion` — RFC 7807 даёт одно `detail` на ответ и словарь «поле → тексты», где код
   и поле разъезжаются по параллельным массивам.
4. **Слои были смешаны.** `Error.Field` (понятие запроса) лежал в `Koto.Domain`; конфликт параллельной записи
   в agent-server летел исключением (`BlueprintConflictException`) между слоями, потому что `Error` не мог нести данные.

Цель — функциональный поток без исключений между слоями: домен возвращает `Result`, Application обогащает,
API превращает в ответ с нужным статусом. Исключения остаются только для неожиданного.

---

## 2. Требования

| # | Требование |
|---|---|
| F1 | Проброс всех ошибок так же короток, как прежний проброс первой |
| F2 | Один формат ответа для HTTP, SignalR и Kafka reply; без полей, дублирующих транспорт (`status`, `title`) |
| F3 | У ошибки есть `details`; для кода контракт «обязательные поля» гарантирован компилятором в точке создания |
| F4 | Домен не знает `Field`, `Details`, HTTP |
| F5 | Граница Application → API типизирована: обычный `Error` в API не попадает |
| F6 | HTTP-статусы остаются осмысленными для инфраструктуры (401-refresh, ретраи 5xx, алерты), но маппинг грубый |
| NF1 | Один тип результата на слой, не более двух на всю систему; никакого `Result<T, E>` |
| NF2 | Без новых внешних зависимостей |

---

## 3. Решение

### 3.1 `Error` — абстрактный record, каталог ошибок — типы

`public abstract record Error(string Code, string Message)`. Инлайновый `new Error(...)` невозможен: каждая
ошибка — record из каталога (`sealed record OtpExpired(DateTimeOffset At) : Error("identity.otp.expired", "…")`).
Свойства record — гарантированные данные ошибки: без них её не сконструировать, ключи `details` — имена
свойств. Код валидируется при создании (≥3 сегмента kebab-case). Каталог машиночитаем: `Koto.Testing.ErrorCatalog`
проверяет формат и уникальность кодов, из него можно генерировать контракт для фронта.

Общие ошибки — nested record'ы `Errors.General.*` с трёхсегментными кодами (`general.entity.not-found`).

### 3.2 `EnrichedError` — декоратор Application-слоя

`public record EnrichedError(Error Inner) : Error(Inner.Code, Inner.Message)` + `Field` + `Details`. Исходная
ошибка сохраняется, код и сообщение копируются. Обогащение явное, три глагола: `ForField(name)`,
`Enrich()` («добавить нечего»), `Enrich(map)` / типизированный record поверх доменной ошибки
(`record MeetupFullWithAlternative(MeetupFull Cause, Guid AlternativeMeetupId) : EnrichedError(Cause)`).
Данные только из базы живут в record'ах Application; домен такой ошибки создать не может по построению.

### 3.3 Два типа результата, граница типизирована

`Result<T>` (домен, `Errors : ErrorList<Error>`) и `AppResult<T>` (хендлеры и диспетчер,
`Errors : ErrorList<EnrichedError>`). Неявной конверсии между ними нет; `Result<T>` не принимается ни одним
методом API-слоя. `ErrorList<TError>` неявно конвертируется в соответствующий результат, поэтому
`return x.Errors.ForField("Email");` и `return x.Errors.Enrich();` так же коротки, как прежний проброс.
Свойство первой ошибки переименовано в `FirstError`: неправильный проброс читается как неправильный.

### 3.4 `Envelope<T>` вместо ProblemDetails

`{ success, result, errors: [{ code, message, field, details }], correlationId, timestamp }` — DTO в
`Koto.Application` (транспорт-независим). `success` — дискриминатор для TypeScript-сужения и для транспортов
без статуса. Успех в HTTP тоже в конверте (решение пользователя: один тип ответа на все транспорты).
Не-JSON ответы (файлы, SSE) вне конверта. Ошибки биндинга FastEndpoints и 500 из exception handler — тот же конверт.

### 3.5 Статус — грубый класс, не второй код

`KotoApiOptions.StatusCodeFor`: exact → rules → `*.not-found` 404 → `*.already-*`/`*.conflict` 409 →
`*.unauthorized` 401 → `*.forbidden` 403 → `general.*`/`validation.*`/есть `Field` 400 → 422. Несколько
ошибок — статус первой (порядок задаёт автор хендлера; `Combine` его сохраняет).

### 3.6 Гарантии — три уровня

1. Компилятор: обязательные данные в точке создания record.
2. Граница API (`EnrichmentGuard`): если для кода существует более полный тип (record, производный от
   `EnrichedError`, с ctor-параметром данного типа), а на провод идёт голый экземпляр — исключение в
   Development и тестах, предупреждение в проде.
3. Словарь `Details` — необязательное, контрактом не гарантируется.

### Последствия

**✅ Положительные:** все ошибки доходят до клиента; один формат на все транспорты; данные для реакции фронта
типизированы; домен чист; каталог ошибок как данные; `WalletClient`-подобный код читает чужие ошибки
структурно (`RemoteError`).

**⚠️ Негативные:** два типа результата вместо одного; `Enrich()` без аргументов будет частым; ≈110 сигнатур
хендлеров и ≈90 мест проброса у потребителей меняются; нестандартный формат ответа требует одной строки в README
и скилле; OpenAPI-схема успеха оборачивается в `Envelope<T>` (базовые эндпоинты объявляют её сами);
204 для void-команд заменён на 200 с конвертом; `timestamp` делает тело успешного ответа нестабильным для ETag.

## 4. Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Профиль ProblemDetails (`errors: [{code,message,field}]` под `application/problem+json`) | От стандарта остаётся только media type; инструменты, ждущие словарь `errors`, ломаются; `status`/`title`/`detail` избыточны |
| Конверт Хорикова с одной ошибкой (`ErrorCode`, `ErrorMessage`, `InvalidField`) | Возвращает первую ошибку; форма с тремя невалидными полями требует трёх отправок |
| `Result<T, TError>` (CSharpFunctionalExtensions) | Обобщённый `E` отклонён в ADR-002; два класса с фиксированным типом ошибки проще читаются |
| Один `Result<T>` на все слои, `EnrichedError : Error` без типовой границы | Не выполняет F5: API принимал бы голые `Error`; гарантия держалась бы только на проверке в рантайме |
| `EnrichedError` наследованием (свой `Code`/`Message`) | Теряется исходная ошибка, дублируются строки кодов в смешанном случае |
| Только словарь `Details`, заполняемый фабрикой | Контракт держится на дисциплине; инлайновый `new Error` его молча нарушает |
| Конверт без успеха (голый DTO на 2xx) | Нет единого типа для SignalR/Kafka; пользователь выбрал один тип ответа на все транспорты |
| Все отказы 400 | Инфраструктура теряет 404/409 без чтения тела; выгода — удаление ~30 строк |

## 5. Риски

1. **Миграция потребителей.** *Меры:* migration note в PLAN.md; изменения механические (сигнатуры) плюс один глагол на проброс; скилл обновлён.
2. **`Enrich()` ставят бездумно, забывая более полный тип.** *Меры:* `EnrichmentGuard` в dev/tests; каталог в `Koto.Testing`.
3. **`details` с вложенными объектами или конфликтующими ключами.** *Меры:* правило «скаляры и массивы, идентификаторы по сущности»; внешние свойства перекрывают внутренние.
4. **Zero-shot клиенты ждут голый DTO.** *Меры:* одна строка в README каждого API-пакета и в скилле; `success` как дискриминатор.
