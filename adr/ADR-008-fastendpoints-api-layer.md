# ADR-008: FastEndpoints как фреймворк API-слоя

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

При построении микросервисов на ASP.NET Core необходимо выбрать способ организации HTTP-эндпоинтов. ASP.NET Core предоставляет несколько подходов: MVC Controllers, Minimal APIs, а также сторонние фреймворки поверх них — Carter и FastEndpoints.

Koto-стек ориентирован на CQRS: каждая операция выражается как команда или запрос, диспетчеризуемая через `ICqrsDispatcher`. HTTP-слой должен органично сочетаться с этой моделью: каждый эндпоинт должен соответствовать одной команде или запросу, не порождая «толстых контроллеров» и не требуя дополнительных медиаторов на уровне HTTP.

Рассматривались следующие варианты: **FastEndpoints**, **Carter**, **MVC Controllers**, **Raw Minimal APIs**, **gRPC**, **GraphQL**.

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| CQRS-выравнивание | Каждый эндпоинт должен однозначно соответствовать одной команде или запросу |
| Валидация | Встроенная интеграция с FluentValidation без ручной проводки |
| Аутентификация и авторизация | Поддержка JWT и политик авторизации на уровне эндпоинта |
| OpenAPI | Автоматическая генерация Swagger/OpenAPI-документации |
| Версионирование API | Встроенная поддержка версионирования эндпоинтов |
| Rate limiting | Ограничение частоты запросов на уровне эндпоинта |
| Интеграция с Koto | Базовые классы `CommandEndpoint<TCommand, TResult>` и `QueryEndpoint<TQuery, TResult>` для автоматической диспетчеризации через `ICqrsDispatcher` |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Производительность | Не хуже Raw Minimal APIs; значительно быстрее MVC Controllers | Высокая |
| Сопровождаемость | Один файл — один эндпоинт; без «жирных контроллеров» | Обязательно |
| Активность сообщества | Фреймворк должен активно поддерживаться (обновления не реже раза в квартал) | Высокая |
| Лицензия | MIT или совместимая | Обязательно |
| Минимальный бойлерплейт | Регистрация эндпоинтов автоматическая; конфигурация через `Configure()` | Высокая |
| Масштабируемость кодовой базы | Подход должен оставаться управляемым при сотнях эндпоинтов | Обязательно |

---

## 3. Решение

### Описание

**FastEndpoints** выбран как стандартный фреймворк API-слоя для всех Koto-микросервисов.

FastEndpoints реализует паттерн **REPR (Request-Endpoint-Response)**: каждый эндпоинт — отдельный класс с единственной ответственностью. Это напрямую отражает модель CQRS: один эндпоинт = одна команда или запрос.

Koto предоставляет базовые классы, соединяющие FastEndpoints с `ICqrsDispatcher`:

```csharp
// Эндпоинт-команда — диспетчеризация выполняется автоматически базовым классом.
public class PlaceOrderEndpoint : CommandEndpoint<PlaceOrderCommand, OrderId>
{
    public override void Configure()
    {
        Post("/orders");
        Roles("Customer");
        Version(1);
    }
    // Метод HandleAsync не нужен: базовый класс передаёт команду в ICqrsDispatcher.
}

// Эндпоинт-запрос — аналогично, без ручной диспетчеризации.
public class GetOrderEndpoint : QueryEndpoint<GetOrderQuery, OrderDto>
{
    public override void Configure()
    {
        Get("/orders/{id}");
        AllowAnonymous();
    }
}

// Валидатор регистрируется автоматически через FluentValidation-интеграцию FastEndpoints.
public class PlaceOrderValidator : Validator<PlaceOrderCommand>
{
    public PlaceOrderValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty();
        RuleFor(x => x.Items).NotEmpty();
    }
}
```

Регистрация в `Program.cs` минимальна:

```csharp
builder.Services
    .AddFastEndpoints()
    .AddKotoCqrs();          // регистрирует ICqrsDispatcher и все хендлеры

app.UseFastEndpoints();
app.UseSwaggerGen();         // встроено в FastEndpoints
```

FastEndpoints работает поверх Minimal APIs, поэтому производительность идентична Raw Minimal APIs. MediatR на HTTP-уровне становится излишним: каждый эндпоинт сам выполняет роль «точки входа» для одной команды или запроса.

### Аргументация

| Критерий | Обоснование |
|---|---|
| Выравнивание с CQRS | REPR-паттерн один-к-одному соответствует модели «команда/запрос → хендлер». Не нужно придумывать, как уложить CQRS в контроллеры, сгруппированные по ресурсам |
| Производительность | FastEndpoints работает поверх Minimal APIs и показывает аналогичные числа в бенчмарках; значительно опережает MVC Controllers |
| Богатый набор функций | FluentValidation, JWT, rate limiting, OpenAPI, версионирование — всё встроено и не требует ручной интеграции |
| Активное сообщество | 5,9 тыс. звёзд на GitHub, последнее обновление — март 2026 г., несколько мейнтейнеров |
| MIT-лицензия | Нет ограничений на коммерческое использование |
| Устранение MediatR на HTTP-уровне | Каждый эндпоинт IS точкой входа для команды/запроса; дополнительный медиатор-посредник не нужен |
| Масштабируемость | Тысячи эндпоинтов остаются управляемыми: каждый — изолированный файл; нет конфликтов при слиянии в контроллерах |

#### Последствия

**✅ Положительные:**
- Кодовая база однородна: один файл — один эндпоинт — одна команда/запрос
- Минимальный бойлерплейт: `Configure()` + опциональный валидатор; диспетчеризация скрыта в базовом классе
- Встроенная поддержка OpenAPI исключает необходимость Swashbuckle/NSwag как отдельных зависимостей
- Валидация применяется автоматически до вызова хендлера — единое место для всех правил
- Производительность не жертвуется ради структуры: FastEndpoints не добавляет накладных расходов сверх Minimal APIs
- MediatR на HTTP-уровне становится избыточным — уменьшается граф зависимостей

**⚠️ Негативные:**
- REPR-паттерн незнаком разработчикам, привыкшим к MVC; требуется обучение
- FastEndpoints — сторонняя зависимость; смена мейнтейнеров или лицензии потребует миграции (прецеденты в экосистеме .NET есть)
- Автоматическая диспетчеризация в базовых классах Koto — «магия», которую нужно понять один раз, но она скрывает поток выполнения от новичков

**↗️ Зависимости:**
- `Koto.Api` (новый пакет) предоставляет базовые классы `CommandEndpoint<,>` и `QueryEndpoint<,>`, зависит от `FastEndpoints` и `Koto.Application`
- Все микросервисы, использующие HTTP-эндпоинты, берут зависимость на `Koto.Api`
- `ICqrsDispatcher` из `Koto.Application` остаётся единственным способом диспетчеризации; FastEndpoints не заменяет его — только вызывает

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Carter** (MIT, 2,4 тыс. звёзд) | Лёгковесный, хорошо интегрируется с Minimal APIs | Один основной мейнтейнер; значительно меньше функций; менее активное развитие (последний мажорный релиз — ноябрь 2024 г.) | FastEndpoints добавляет больше ценности при сопоставимой сложности; Carter не оправдывает предпочтение при такой разнице в экосистеме |
| **MVC Controllers** | Знаком большинству .NET-разработчиков; обширная документация | Группировка по ресурсам конфликтует с CQRS; «жирные контроллеры» — типичная проблема; много бойлерплейта; ниже производительность | Не соответствует CQRS-первому подходу Koto; ведёт к архитектурным компромиссам, которые ADR-серия стремится предотвратить |
| **Raw Minimal APIs** | Максимальная производительность; минимальные зависимости; встроено в ASP.NET Core | При сотнях эндпоинтов `Program.cs` превращается в хаос; нет стандартной структуры; валидацию, OpenAPI, версионирование подключаем вручную | FastEndpoints — это Minimal APIs с добавленной структурой; производительность идентична, опыт разработчика лучше |
| **gRPC** | Отличная производительность; строгий контракт через Protobuf; двусторонний стриминг | Не подходит для внешних API (браузеры, мобильные клиенты); требует Protobuf-тулчейн; REST всё равно нужен | Рассматривается как дополнение для внутреннего межсервисного взаимодействия, но не как замена REST для внешних API |
| **GraphQL** | Гибкие запросы; единый эндпоинт | Не универсален; REST по-прежнему нужен для большинства интеграций; дополнительная сложность схемы | Может применяться как дополнение, но не как основной транспорт; выходит за рамки данного ADR |

### 5. Риски

1. **Смена лицензии или заброшенность FastEndpoints**  
   *Меры:* Изолировать зависимость на FastEndpoints внутри `Koto.Api`; все микросервисы взаимодействуют через базовые классы Koto, а не напрямую с FastEndpoints API. При необходимости миграции потребуется изменить только `Koto.Api`, не трогая хендлеры бизнес-логики. Мониторить репозиторий FastEndpoints на предмет изменений лицензии.

2. **Кривая обучения для новых участников**  
   *Меры:* Задокументировать REPR-паттерн и базовые классы Koto в CONTRIBUTING.md с примерами. Добавить шаблоны эндпоинтов (dotnet new template) для быстрого старта. Ссылаться на настоящий ADR в ревью PR при вопросах «почему не контроллеры».

3. **«Магия» автоматической диспетчеризации затрудняет отладку**  
   *Меры:* Базовые классы `CommandEndpoint<,>` и `QueryEndpoint<,>` должны быть намеренно короткими и читаемыми (< 30 строк). Добавить подробные XML-комментарии. Трассировка через OpenTelemetry покрывает весь путь от эндпоинта до хендлера.

4. **Конфликты версий FastEndpoints между микросервисами**  
   *Меры:* Версия FastEndpoints фиксируется в `Directory.Packages.props` (Central Package Management); все микросервисы используют одну и ту же версию транзитивно через `Koto.Api`. Обновление версии — единственное изменение в одном месте.

5. **Разрастание `Koto.Api` до «швейцарского ножа»**  
   *Меры:* `Koto.Api` содержит только базовые классы эндпоинтов и конфигурацию FastEndpoints. Любое расширение требует отдельного ADR. Кандидаты на вынос: middleware, фильтры исключений, проблемные детали (ProblemDetails).
