# ADR-015: ArchUnitNET для архитектурных Fitness Functions в Koto.Testing.Architecture

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

Архитектура деградирует со временем. Разработчики делают «временные» обходные пути, которые становятся паттернами. Новые члены команды не знают правил. Давление сроков приводит к срезанию углов. Архитектура, зафиксированная только в вики, не читается и не исполняется.

Концепция **Fitness Functions** (из книги «Building Evolutionary Architectures» Форда, Парсонса и Куа) — это автоматизированные тесты, которые непрерывно верифицируют архитектурные характеристики системы. Они запускаются в CI точно так же, как юнит-тесты, и падают при нарушении архитектурных правил.

Типичные причины архитектурной деградации:
- Нарушения «только один раз», которые становятся прецедентами
- Новые разработчики, не знакомые с принятыми решениями
- Временное давление сроков, ведущее к срезанию углов
- Архитектура, задокументированная только в вики, которую никто не читает

**ArchUnitNET** — порт библиотеки Java ArchUnit для платформы .NET:
- Лицензия Apache 2.0, активно поддерживается
- Анализирует .NET-сборки через рефлексию
- Fluent API для декларативного описания архитектурных правил
- Интегрируется с xUnit, NUnit, MSTest — запускается как обычный тест

**`Koto.Testing.Architecture`** — обёртка над ArchUnitNET с предварительно настроенными правилами для архитектуры Koto, что позволяет командам применять Fitness Functions без необходимости описывать правила с нуля.

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Проверка слоёв Clean Architecture | Система должна автоматически верифицировать, что Domain не зависит от Application, Infrastructure и Api; Application — только от Domain; Infrastructure — не от Api; Api — не от Infrastructure напрямую |
| Соглашения об именовании | Система должна проверять, что доменные события оканчиваются на `DomainEvent`, команды — на `Command`, запросы — на `Query` |
| Пользовательские правила | Система должна позволять командам определять произвольные архитектурные правила через Fluent API ArchUnitNET |
| Запрет прямого использования типов | Система должна выявлять прямое обращение к запрещённым типам (например, `DateTime` в Domain вместо `IClock`) |
| Интеграция с CI | Все архитектурные тесты должны запускаться как обычные xUnit-тесты в пайплайне CI и падать при нарушении правил |
| Диагностические сообщения | При нарушении правила тест должен выводить понятное сообщение с указанием нарушающего класса и причины правила |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Нулевые зависимости в продакшн-коде | `Koto.Testing.Architecture` должна быть зависимостью только тестовых проектов; продакшн-сборки не должны ссылаться на неё | Обязательно |
| Скорость выполнения | Полный набор архитектурных тестов должен выполняться менее чем за 30 секунд, чтобы не замедлять CI | Высокая |
| Низкий порог входа | Подключение стандартных правил Koto должно занимать не более 10 строк кода без знания внутренностей ArchUnitNET | Высокая |
| Расширяемость | Команды должны иметь возможность добавлять собственные правила поверх предоставляемых Koto без модификации библиотеки | Высокая |
| Стабильность | Архитектурные тесты не должны давать ложноположительных срабатываний при рефакторинге, не нарушающем архитектурные границы | Высокая |

---

## 3. Решение

### Описание

Принята библиотека **ArchUnitNET** в качестве движка для архитектурных Fitness Functions. Поверх неё создаётся пакет **`Koto.Testing.Architecture`**, предоставляющий предварительно настроенные правила для архитектуры Koto.

Библиотека предоставляет три уровня API:

**1. Предварительно настроенные правила для слоёв Clean Architecture:**

```csharp
[Fact]
public void CleanArchitecture_Layers_HaveCorrectDependencies()
    => KotoLayerRules.ForCleanArchitecture(
        domainAssembly: typeof(Order).Assembly,
        applicationAssembly: typeof(PlaceOrderCommand).Assembly,
        infrastructureAssembly: typeof(AppDbContext).Assembly,
        apiAssembly: typeof(PlaceOrderEndpoint).Assembly
    ).Check(arch);
```

`KotoLayerRules.ForCleanArchitecture` проверяет четыре инварианта:
1. Domain не зависит от Application, Infrastructure и Api
2. Application зависит только от Domain (никаких EF Core, Wolverine, Kafka)
3. Infrastructure не зависит от Api
4. Api не зависит от Infrastructure напрямую (только через Application)

**2. Предварительно настроенные правила именования:**

```csharp
[Fact]
public void DomainEvents_MustEndWith_DomainEvent()
    => KotoNamingRules.DomainEventsSuffix(domainAssembly).Check(arch);
```

**3. Пользовательские правила через Fluent API ArchUnitNET:**

```csharp
[Fact]
public void Domain_ShouldNotUse_DateTime_Directly()
    => KotoArchitecture
        .Classes().In(domainAssembly)
        .ShouldNot().AccessMembersOf(typeof(DateTime))
        .BecauseOf("Use IClock abstraction for testability")
        .Check(arch);
```

Добавление `using Microsoft.EntityFrameworkCore` в Domain-проект немедленно приводит к падению теста `CleanArchitecture_Layers_HaveCorrectDependencies` в CI.

### Аргументация

| Критерий | Обоснование |
|---|---|
| Автоматическое исполнение | Fitness Functions запускаются в CI при каждом PR; нарушение не может попасть в основную ветку незамеченным, в отличие от документации или ручного code review |
| Fluent API понятен без изучения документации | Правила читаются как спецификация: `Classes().In(domainAssembly).ShouldNot().AccessMembersOf(typeof(DbContext))` |
| Анализ на уровне IL | ArchUnitNET проверяет фактические зависимости в скомпилированных сборках, а не проектные ссылки; выявляет неявные зависимости через рефлексию |
| Активное сообщество и сопровождение | Активно поддерживаемый проект, порт устоявшейся Java-библиотеки с многолетней историей |
| Лицензия Apache 2.0 | Совместима с коммерческим использованием без ограничений |
| Обёртка снижает порог входа | `Koto.Testing.Architecture` скрывает сложность ArchUnitNET; команды подключают 3–5 строк для получения полного набора проверок |

#### Последствия

**Положительные:**
- Нарушения архитектурных границ выявляются в CI, а не на production или случайно при code review
- Новые разработчики не могут непреднамеренно нарушить архитектуру — тесты объяснят правила
- Архитектурные решения, зафиксированные в коде, всегда актуальны в отличие от документации в вики
- Добавление пользовательских правил не требует изменения библиотеки — достаточно написать новый тест
- Диагностические сообщения с `BecauseOf` объясняют причину правила прямо в выводе тестов

**Негативные:**
- Необходимо поддерживать набор архитектурных тестов: при добавлении нового слоя или переименовании пространства имён тесты нужно обновлять
- Ложноотрицательные результаты возможны для очень сложных сценариев (например, зависимости через дженерики или рефлексию), которые ArchUnitNET не всегда отслеживает
- Время на обучение: разработчики должны понимать, что делать при падении архитектурного теста

**Зависимости:**
- `Koto.Testing.Architecture` зависит от `ArchUnitNET` и `xunit` — только как тестовые зависимости
- Каждый микросервис создаёт тестовый проект `*.Architecture.Tests`, ссылающийся на `Koto.Testing.Architecture`
- Продакшн-сборки (Domain, Application, Infrastructure, Api) не имеют зависимости от `Koto.Testing.Architecture`
- CI-пайплайн должен включать запуск архитектурных тестов наряду с юнит- и интеграционными тестами

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Ручной code review** | Не требует дополнительных инструментов; проверяющий видит контекст | Не масштабируется; человеку легко пропустить нарушение под давлением сроков; не работает в 3 часа ночи в hotfix-ветке | Работает лучше, чем ничего, но не является систематической защитой; не исключает нарушения |
| **Ограничения проектных ссылок в .csproj** | Исполняется компилятором; нулевые зависимости | Проверяет только явные ссылки на проекты, но не использование пространств имён; не помогает против `PackageReference` на запрещённые NuGet-пакеты в нужном слое | Неполная защита: Domain может добавить `<PackageReference Include="Microsoft.EntityFrameworkCore"/>` без проектной ссылки на Infrastructure |
| **NetArchTest (MIT)** | Похожий API; MIT-лицензия; меньше зависимостей | Менее мощный API по сравнению с ArchUnitNET; меньшее сообщество; разработка менее активна | ArchUnitNET предоставляет более богатый набор предикатов и лучшую документацию; инвестиции в изучение оправданы богатством API |
| **Roslyn-анализаторы** | Анализ во время компиляции; диагностика в IDE в реальном времени; максимальная гибкость | Значительная сложность разработки и сопровождения; требует глубокого знания Roslyn API; собственный анализатор сложно отлаживать | Избыточная инженерная сложность для данного случая; ArchUnitNET покрывает 95% потребностей при 10% усилий |
| **Только документация** | Нулевые затраты на разработку | Документация не исполняется; устаревает; игнорируется при давлении сроков; новые разработчики её не читают | Задокументированная архитектура без автоматического исполнения — архитектура на словах, а не на деле |

### 5. Риски

1. **Ложноотрицательные срабатывания — нарушения, не выявленные тестами**  
   ArchUnitNET анализирует IL-код и может не выявить зависимости, введённые через рефлексию, `dynamic`, source generators или сложные дженерик-конструкции.  
   *Меры:* Дополнять Fitness Functions ручным code review для высокорискованных PR; расширять набор правил по мере выявления таких паттернов.

2. **Устаревание архитектурных тестов при рефакторинге**  
   При переименовании пространств имён, добавлении новых слоёв или реструктуризации проекта архитектурные тесты могут начать ошибочно падать или, наоборот, перестать проверять нужное.  
   *Меры:* Включать обновление архитектурных тестов в Definition of Done для задач на рефакторинг; проверять тесты в рамках архитектурных ревью.

3. **«Закрытие» CI без понимания причин**  
   Разработчик, видя падение архитектурного теста, может отключить его или добавить исключение, не разобравшись в причине.  
   *Меры:* Требовать явного одобрения tech lead для любого изменения в `*.Architecture.Tests`; вести в ADR историю причин добавления каждого правила; использовать `BecauseOf` во всех правилах.

4. **Производительность при росте числа правил**  
   ArchUnitNET загружает и анализирует сборки целиком; при большом числе правил и крупных сборках время выполнения может превысить допустимый порог в 30 секунд.  
   *Меры:* Кешировать загрузку сборок на уровне test fixture (`IClassFixture` в xUnit); профилировать при добавлении более 20 правил в один тестовый проект; при необходимости выделять архитектурные тесты в отдельный CI-шаг с параллельным запуском.
