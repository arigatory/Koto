# ADR-016: Автомасштабирование Kafka-консьюмеров через KEDA вместо CPU-based HPA

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В Kubernetes стандартный Horizontal Pod Autoscaler (HPA) масштабирует поды на основе загрузки CPU или памяти. Этот подход хорошо работает для HTTP-сервисов, где нагрузка на CPU коррелирует с количеством входящих запросов.

Для Kafka-консьюмеров картина принципиально иная. Консьюмер большую часть времени находится в режиме ожидания сообщений — CPU при этом остаётся низким, даже если consumer group lag (число необработанных сообщений в топике) стремительно растёт. При всплеске сообщений CPU ненадолго возрастает, однако к тому моменту, когда HPA отреагирует (cooldown по умолчанию — 5 минут), в топике уже накоплены тысячи сообщений, а задержка обработки критически вырастает. В обратной ситуации — когда трафик прекращается — CPU падает мгновенно, хотя lag ещё не исчерпан.

Правильная метрика для Kafka-консьюмеров — **consumer group lag**: количество сообщений в топике, которые ещё не обработаны консьюмерами.

- Lag = 0 → консьюмеры успевают, можно масштабировать вниз.
- Lag = 500 → умеренная нагрузка, текущее число реплик достаточно.
- Lag = 5000 → требуется немедленное масштабирование вверх.

KEDA (Kubernetes Event-Driven Autoscaler) — проект CNCF (статус Graduated), лицензия Apache 2.0 — расширяет стандартный HPA кастомными скейлерами. Kafka-скейлер KEDA напрямую считывает consumer group lag из брокера и масштабирует поды на его основе, а не по CPU.

Решение распространяется на все сервисы, использующие `IntegrationEventConsumerBase` из `Koto.Messaging.Wolverine`: потоковые процессоры, участники саг, консьюмеры уведомлений.  
**Не применяется** к HTTP/gRPC-сервисам (для них используется стандартный CPU-based HPA) и к batch-задачам (K8s CronJob с фиксированным параллелизмом).

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Метрика масштабирования | Автомасштабирование должно опираться на consumer group lag, а не на CPU или память |
| Немедленная реакция | При появлении lag выше порога новые поды должны запускаться без многоминутного cooldown |
| Масштабирование вниз | При снижении lag до нуля лишние реплики должны высвобождаться для экономии ресурсов |
| Минимальная доступность | Каждый Kafka-консьюмер должен иметь не менее одной реплики в любой момент времени |
| Ограничение максимума | Должен быть явный потолок реплик, не допускающий неконтролируемого роста |
| Декларативная конфигурация | Параметры масштабирования должны задаваться манифестом в репозитории (GitOps) |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Время реакции | Задержка между ростом lag и стартом новых подов не должна превышать 30 секунд | Обязательно |
| Производительность | Опрос Kafka по lag не должен создавать значимой нагрузки на брокер | Высокая |
| Наблюдаемость | Текущий lag и число реплик должны быть доступны в Prometheus/Grafana | Высокая |
| Отказоустойчивость | Недоступность KEDA Operator не должна останавливать уже запущенные поды | Обязательно |
| Совместимость | KEDA должна работать поверх стандартного Kubernetes HPA без замены его API | Средняя |
| Единообразие | Конфигурация ScaledObject должна следовать единому шаблону для всех Kafka-консьюмеров проекта | Средняя |

## 3. Решение

### Описание

**Для всех сервисов на базе `IntegrationEventConsumerBase` используется KEDA с Kafka-скейлером вместо CPU-based HPA.**

Каждый Kafka-консьюмер получает манифест `ScaledObject`, описывающий правила масштабирования:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: orders-processor-scaler
  namespace: orders
spec:
  scaleTargetRef:
    name: orders-processor          # имя Deployment
  minReplicaCount: 1
  maxReplicaCount: 20
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: orders-processor-group
        topic: orders.order-placed
        lagThreshold: "100"         # 1 дополнительная реплика на каждые 100 необработанных сообщений
        offsetResetPolicy: latest
```

**Как работает алгоритм масштабирования:**

1. KEDA Operator с заданным интервалом (по умолчанию 30 секунд) опрашивает Kafka и получает текущий consumer group lag.
2. Желаемое число реплик вычисляется как `ceil(lag / lagThreshold)`, но не менее `minReplicaCount` и не более `maxReplicaCount`.
3. KEDA обновляет стандартный HPA с вычисленным целевым значением, HPA управляет Deployment.
4. При lag = 0 KEDA может масштабировать Deployment до 0 реплик, если разрешено (`minReplicaCount: 0`); в проекте используется `minReplicaCount: 1` для гарантии наличия хотя бы одного консьюмера.

**Пример реакции на всплеск нагрузки:**

| Момент времени | Consumer lag | Реплики |
|---|---|---|
| T+0 с | 10 000 | 1 (исходное состояние) |
| T+30 с | 9 500 | 20 (maxReplicaCount, KEDA среагировал) |
| T+5 мин | 2 000 | 20 |
| T+10 мин | 0 | постепенное снижение до 1 |

**Шаблон ScaledObject** хранится в `k8s/templates/kafka-scaledobject.yaml` и параметризуется через Helm values.

### Аргументация

| Критерий | Обоснование |
|---|---|
| Правильная метрика | Consumer group lag напрямую отражает реальную нагрузку на консьюмер. CPU этого не делает: консьюмер простаивает при высоком lag и нагружает CPU при обработке — корреляции нет |
| Скорость реакции | KEDA реагирует за 15–30 секунд против 3–5 минут у CPU HPA из-за cooldown-периода. При burst в 10 000 сообщений это критично |
| Зрелость и поддержка | KEDA — CNCF Graduated проект с активным community, используется в production у множества компаний. Не эксперимент |
| Нативная интеграция | KEDA расширяет, а не заменяет стандартный HPA. Kubernetes-инструменты (kubectl, мониторинг HPA) продолжают работать |
| Декларативность | ScaledObject — обычный CRD, хранится в git рядом с остальными манифестами. GitOps-подход сохраняется |
| Экономия ресурсов | В периоды низкой нагрузки число реплик снижается автоматически. Фиксированное число реплик потребляло бы CPU/память впустую |
| Наблюдаемость | KEDA экспортирует метрики в Prometheus: `keda_scaler_metrics_value` (lag), `keda_scaled_object_paused`, число желаемых реплик |

#### Последствия

**Положительные:**
- Масштабирование происходит по реально значимой метрике — накопленному lag — а не по косвенному индикатору (CPU).
- Время реакции на всплеск нагрузки сокращается с нескольких минут до 30 секунд.
- При lag = 0 число реплик автоматически снижается, сокращая затраты на инфраструктуру в периоды простоя.
- Конфигурация масштабирования вынесена в отдельный манифест и версионируется в git вместе с остальными ресурсами сервиса.
- KEDA не требует изменений в коде самих консьюмеров.

**Негативные:**
- Требуется установка и сопровождение KEDA Operator в кластере (ещё один компонент инфраструктуры).
- Команде необходимо освоить концепцию ScaledObject / CRD и разобраться с отладкой масштабирования через KEDA.
- При неверно подобранном `lagThreshold` возможно агрессивное масштабирование (слишком много реплик) или запоздалое (слишком мало).
- Масштабирование ограничено числом партиций топика: больше реплик, чем партиций, не имеет смысла — лишние поды простаивают без назначенных партиций.

**Зависимости:**
- KEDA Operator должен быть установлен в кластере (`helm install keda kedacore/keda`).
- Все Kafka-консьюмеры проекта используют `IntegrationEventConsumerBase` из `Koto.Messaging.Wolverine` — это единая точка входа, что упрощает внедрение единого шаблона ScaledObject.
- Число партиций в Kafka-топике должно быть не меньше `maxReplicaCount` консьюмера, иначе часть реплик останется без работы.
- ADR-006 (Wolverine как messaging backbone) и ADR-011 (Integration Events через Kafka) остаются в силе: KEDA управляет только числом реплик, не затрагивая логику обработки сообщений.

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **CPU-based HPA (стандартный)** | Встроен в Kubernetes, не требует дополнительных компонентов | CPU консьюмера не коррелирует с lag: при ожидании сообщений CPU низкий, HPA не масштабирует; cooldown 5 минут при всплеске — слишком медленно | Неправильная метрика для event-driven нагрузки; принципиально не решает задачу |
| **Memory-based HPA** | Встроен в Kubernetes | Та же проблема, что с CPU: потребление памяти Kafka-консьюмером не зависит от lag | Неправильная метрика, аналогично CPU HPA |
| **Custom Metrics Adapter (Prometheus Adapter)** | Позволяет использовать любую Prometheus-метрику, включая lag | Требует настройки Prometheus Adapter, написания PromQL-запросов, ручной конфигурации HPA с внешними метриками; значительно сложнее в сопровождении | KEDA реализует то же самое из коробки с Kafka-скейлером без ручной настройки adapter + HPA |
| **Фиксированное число реплик** | Предельная простота; нет зависимостей от внешних компонентов | Перерасход ресурсов при низком трафике; нехватка реплик при всплесках; требует ручного вмешательства при изменении нагрузки | Не решает задачу автомасштабирования; неприемлемо для production с переменной нагрузкой |
| **Prometheus-based HPA с custom metrics** | Гибкость; можно комбинировать несколько метрик | Более сложная настройка, чем KEDA: Prometheus Adapter + HPA v2 custom metrics; lag нужно экспортировать через Kafka Exporter | KEDA инкапсулирует эту сложность и предоставляет готовый Kafka-скейлер; менее кода для сопровождения |

### 5. Риски

1. **Неверный `lagThreshold` приводит к избыточному или недостаточному масштабированию**  
   Если порог выставлен слишком низко, кластер будет запускать лишние поды при незначительном lag. Если слишком высоко — реакция запаздывает.  
   *Меры:* Начинать с консервативного значения (100–500 сообщений на реплику). После первого месяца в production провести анализ метрик `keda_scaler_metrics_value` и скорректировать `lagThreshold` под реальные характеристики нагрузки. Значение выносится в Helm values — изменение не требует пересборки образа.

2. **Ограничение числа партиций Kafka**  
   Kafka назначает не более одного консьюмера из группы на партицию. Если `maxReplicaCount` превышает число партиций, лишние поды будут запущены, но не получат сообщений — пустой расход ресурсов.  
   *Меры:* Зафиксировать правило: `maxReplicaCount` ≤ количество партиций топика. Добавить это в чеклист PR для сервисов, получающих ScaledObject.

3. **Сбой KEDA Operator**  
   При недоступности KEDA Operator автомасштабирование прекращается. Уже запущенные поды продолжают работать, но реакции на изменение lag нет.  
   *Меры:* Развернуть KEDA Operator с не менее чем 2 репликами (`replicaCount: 2` в Helm values). Добавить алерт в Grafana на отсутствие метрик KEDA более 2 минут. Прописать fallback-процедуру в Runbook: ручное изменение `spec.replicas` в Deployment до восстановления KEDA.

4. **Слишком агрессивное масштабирование вниз при «пульсирующем» трафике**  
   При чередовании коротких всплесков и пауз KEDA может масштабировать вниз между всплесками, что вызовет повторный холодный старт подов.  
   *Меры:* Настроить `cooldownPeriod` в ScaledObject (по умолчанию 300 секунд) в соответствии с характером нагрузки конкретного сервиса. При необходимости увеличить до 600 секунд для сервисов с пульсирующим трафиком.

5. **Версионирование и обновление KEDA Operator**  
   Обновление KEDA может изменить поведение скейлеров или API ScaledObject.  
   *Меры:* Фиксировать версию KEDA в Helm values (`version: 2.x.y`). Обновления проводить в staging-окружении с проверкой масштабирования под нагрузкой перед выкаткой в production.
