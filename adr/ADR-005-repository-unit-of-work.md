# ADR-005: Интерфейс IRepository<TAgg, TId> — совместимость с Unit of Work, без SaveAsync

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В проекте используется Domain-Driven Design и EF Core. Необходимо определить контракт репозитория для агрегатов. Ключевые вопросы: должен ли репозиторий сам коммитить изменения (`SaveAsync`)? Должны ли `Add` и `Delete` быть асинхронными? Как обеспечить атомарность при изменении нескольких агрегатов в одной транзакции?

EF Core `DbContext` сам по себе реализует паттерн Unit of Work: он отслеживает все изменения и фиксирует их единым вызовом `SaveChangesAsync()`. Дублирование этой ответственности в репозитории нарушает разделение обязанностей и делает управление транзакциями невозможным из прикладного слоя.

---

## 2. Требования

### Функциональные

| # | Требование |
|---|-----------|
| F1 | Метод `GetByIdAsync(TId id, CancellationToken ct)` — асинхронное чтение агрегата по идентификатору |
| F2 | Метод `Add(TAgg aggregate)` — синхронная регистрация агрегата для добавления в БД |
| F3 | Метод `Delete(TAgg aggregate)` — синхронная регистрация агрегата для удаления из БД |
| F4 | Репозиторий обобщён по типу агрегата `TAgg : AggregateRoot<TId>` и его идентификатора `TId` |
| F5 | Коммит изменений производится прикладным слоем через `DbContext.SaveChangesAsync()` — вне репозитория |
| F6 | При изменении нескольких агрегатов в одном обработчике команды все изменения фиксируются атомарно |

### Нефункциональные

| # | Требование |
|---|-----------|
| NF1 | Интерфейс репозитория не содержит `SaveAsync` — ответственность за коммит лежит на прикладном слое |
| NF2 | `Add` и `Delete` синхронны: они не производят I/O и не должны создавать ложное ожидание асинхронной операции |
| NF3 | Интерфейс минимален — только то, что нужно для базового CRUD-взаимодействия с агрегатами |
| NF4 | Совместимость с паттерном Unit of Work (EF Core DbContext) без дополнительных абстракций |
| NF5 | Управление жёсткими удалениями остаётся возможным, но предпочтительны мягкие удаления через доменное состояние |

---

## 3. Решение

### Описание

Контракт репозитория определён следующим образом:

```csharp
public interface IRepository<TAgg, TId>
    where TAgg : AggregateRoot<TId>
{
    Task<TAgg?> GetByIdAsync(TId id, CancellationToken ct = default);
    void Add(TAgg aggregate);       // sync — только помечает в change tracker
    void Delete(TAgg aggregate);    // sync — только помечает в change tracker
}
// SaveAsync отсутствует — коммит НЕ является ответственностью репозитория
```

**Почему `GetByIdAsync` асинхронен:** Чтение из базы данных — это I/O. Асинхронность здесь обязательна, чтобы не блокировать поток.

**Почему `Add` и `Delete` синхронны:** Оба метода вызывают лишь `DbContext.Add()` / `DbContext.Remove()` — никакого I/O, никакого обращения к БД. Добавление `async` было бы семантически ложным и вводило бы в заблуждение вызывающий код.

**Почему нет `SaveAsync`:** `DbContext` в EF Core является Unit of Work. Прикладной слой (обработчик команды) вызывает `DbContext.SaveChangesAsync()`, который атомарно фиксирует все накопленные изменения. Если `SaveAsync` находится в репозитории — теряется атомарность при работе с несколькими агрегатами, концепция UoW дублируется, а управление транзакциями из прикладного слоя становится невозможным.

Корректный паттерн использования:

```csharp
// Обработчик команды (прикладной слой):
public async Task<Result<Unit>> HandleAsync(CancelOrderCommand cmd, CancellationToken ct)
{
    var order = await _orderRepo.GetByIdAsync(cmd.OrderId, ct);
    if (order is null) return Errors.General.NotFound("order", cmd.OrderId);

    var result = order.Cancel(cmd.Reason);
    if (result.IsFailure) return result.Error;

    _orderRepo.Delete(order);           // помечает для удаления
    await _db.SaveChangesAsync(ct);     // фиксирует всё атомарно
    return Unit.Value;
}
```

**Удаление в доменном контексте:** Жёсткие удаления в DDD встречаются редко. Чаще «удаление» — это изменение доменного состояния (`order.Cancel()`, `user.Deactivate()`). Метод `Delete()` в репозитории сохраняется для случаев, когда физическое удаление действительно необходимо, однако мягкие удаления через доменное состояние предпочтительны.

**Примечание для Event Sourcing (Marten):** Репозиторий на основе Event Sourcing содержит `SaveAsync` — и это корректно, поскольку Marten не использует UoW/DbContext; каждая запись событий является самостоятельной операцией. Данный подход задокументирован в ADR-007.

### Аргументация

| Аргумент | Пояснение |
|----------|-----------|
| Атомарность транзакций | Обработчик команды может изменить несколько агрегатов и сохранить их единым `SaveChangesAsync()` — без риска частичного коммита |
| EF Core DbContext — уже UoW | Дублировать паттерн Unit of Work в репозитории бессмысленно и вредно |
| Синхронные Add/Delete не вводят в заблуждение | Вызывающий код ясно видит: эти операции не производят I/O |
| Минимальный интерфейс | Репозиторий отвечает только за доступ к агрегатам, а не за управление транзакциями |
| Управление транзакциями из прикладного слоя | Обработчик команды контролирует границы транзакции — это его прямая ответственность |
| Мягкие удаления предпочтительны | Физическое удаление через `Delete()` доступно, но доменные методы (`Cancel`, `Deactivate`) более выразительны |

#### Последствия

**Положительные:**
- Атомарность транзакций гарантирована: все изменения одного обработчика команды сохраняются вместе или не сохраняются вовсе
- Интерфейс репозитория остаётся минимальным и не смешивает ответственности
- Прикладной слой явно управляет границами транзакций
- Синхронные `Add`/`Delete` корректно отражают семантику: никакого I/O не происходит

**Отрицательные:**
- Разработчики, незнакомые с паттерном UoW, могут искать `SaveAsync` в репозитории
- Необходимо явно внедрять `DbContext` (или аналогичную абстракцию) в обработчики команд для вызова `SaveChangesAsync()`
- Event Sourcing требует иного подхода (Marten, `SaveAsync`) — два разных контракта для разных видов репозиториев

**Зависимости:**
- Все обработчики команд, изменяющие агрегаты, должны явно вызывать `DbContext.SaveChangesAsync()`
- Event Sourcing-репозитории следуют собственному контракту (ADR-007)
- Мягкие удаления реализуются через доменные методы агрегатов, а не через `Delete()` репозитория

---

### 4. Альтернативы

| Альтернатива | Причина отклонения |
|-------------|-------------------|
| Включить `SaveAsync` в репозиторий | Нарушает атомарность при работе с несколькими агрегатами; дублирует паттерн UoW; делает управление транзакциями из прикладного слоя невозможным |
| Использовать `DeleteAsync` вместо `Delete` | Вводит в заблуждение: метод не производит I/O и лишь вызывает `DbContext.Remove()` внутри |
| Сервисный репозиторий (управляет полным жизненным циклом) | Смешивает ответственности репозитория и сервиса; нарушает SRP |
| Базовый обобщённый класс с методом `Save` | Избыточная инженерия; добавляет сложность без ощутимой выгоды |

---

### 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Разработчик забывает вызвать `SaveChangesAsync()` в обработчике | Средняя | Высокое | Code review; интеграционные тесты, проверяющие персистентность; линтер/анализатор, предупреждающий об отсутствии вызова |
| Разработчик добавляет `SaveAsync` в конкретную реализацию репозитория | Низкая | Среднее | Зафиксировать контракт в ADR; проверять на code review; не выставлять метод через интерфейс |
| Путаница между EF Core-репозиторием и Event Sourcing-репозиторием | Средняя | Среднее | Чёткая документация в ADR-007; именование типов и пространств имён, явно указывающее на вид хранилища |
| Жёсткое удаление используется там, где нужно мягкое | Средняя | Среднее | Договориться о соглашении: жёсткое удаление только по явному бизнес-требованию; предпочитать доменные методы |
| Сложность отладки при нескольких агрегатах в одной транзакции | Низкая | Низкое | Логировать вызовы `SaveChangesAsync()`; использовать перехватчики EF Core для диагностики |

## Ревизия 2026-07-04 (v0.3.0-preview.1)

**`IRepository<TAgg, TId>` перенесён из `Koto.Domain` в `Koto.Application`** (namespace `Koto.Application`, файл `Persistence/IRepository.cs`). Контракт не изменился — только слой.

Мотивация:

- **Порт живёт со своим потребителем.** Домен репозитории не использует: агрегаты не зовут репозитории, единственный потребитель `IRepository` — обработчики команд/запросов на application-слое (Ports & Adapters).
- **Две половины одного контракта — в одном слое.** `Add`/`Delete` документированы как «запись случится при коммите Unit of Work», а `IUnitOfWork` всегда жил в `Koto.Application`. Теперь `IRepository` и `IUnitOfWork` соседствуют.
- **Домен полностью чист.** В `Koto.Domain` остаются только сущности, value objects, события и `Result` — «кричащая архитектура» доменного слоя.

Миграция для потребителей: заменить `using Koto.Domain;` на `using Koto.Application;` в местах использования `IRepository` (constraint `TAgg : AggregateRoot<TId>` по-прежнему ссылается на `Koto.Domain`).
