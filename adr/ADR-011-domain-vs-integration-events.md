# ADR-011: Строгое разделение Domain Events и Integration Events как разных типов

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В архитектуре Koto агрегаты порождают события, чтобы сообщать об изменениях состояния. Эти события используются в двух принципиально разных сценариях:

1. **Внутри сервиса** — обновление read-модели, отправка email, запуск бизнес-логики в рамках одной транзакции или сразу после неё.
2. **Между сервисами** — уведомление других микросервисов через брокер сообщений (Kafka) об изменениях, которые им важны.

Возник вопрос: использовать ли единый тип события для обоих сценариев или разделить их на два самостоятельных типа с явным преобразованием между ними?

Wolverine используется как Outbox и как диспетчер: после `SaveChangesAsync` он асинхронно доставляет события из базы данных к in-process обработчикам. Обработчик, в свою очередь, принимает решение — публиковать ли Integration Event в Kafka.

Полный поток выглядит следующим образом:

```
Aggregate.SomeBehavior()
  └─ AddDomainEvent(new OrderPlacedDomainEvent(...))    // внутренний, приватный контракт

DbContext.SaveChangesAsync()
  └─ Wolverine Outbox: {бизнес-данные + domain event} → единый коммит в БД

Wolverine (асинхронно из Outbox) диспетчеризует in-process обработчику:
  └─ OrderPlacedDomainEventHandler
       ├─ обновляет read-модель (EF Core проекция)
       ├─ отправляет email-уведомление
       └─ publisher.PublishAsync(new OrderPlacedIntegrationEvent(...)) → Kafka
              └─ другие микросервисы потребляют его
```

---

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Внутренняя реактивность | Агрегаты должны иметь возможность порождать события, которые обрабатываются внутри сервиса без публикации во внешний брокер |
| Межсервисная коммуникация | Сервис должен публиковать события в Kafka для потребления другими микросервисами |
| Явное преобразование | Должен существовать явный шаг трансляции между внутренним событием и публикуемым — не автоматический |
| Избирательная публикация | Не каждое Domain Event обязано порождать Integration Event; обработчик сам принимает это решение |
| Идемпотентность | Integration Events должны нести `EventId`, позволяющий потребителям безопасно обрабатывать дубли |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Независимость контрактов | Изменение Domain Event не должно автоматически ломать контракт Integration Event | Обязательно |
| Слабое зацепление | Внутренняя доменная модель не должна утекать во внешний публичный контракт | Обязательно |
| Версионирование | Integration Events должны поддерживать эволюцию схемы с сохранением обратной совместимости | Высокая |
| Прозрачность границы | Место трансляции между внутренним и внешним контрактом должно быть явным и легко находимым | Высокая |
| Расположение типов | `IDomainEvent` принадлежит `Koto.Domain`; `IIntegrationEvent` принадлежит `Koto.Application` | Средняя |

---

## 3. Решение

### Описание

**Domain Events и Integration Events реализуются как два отдельных типа с явным ручным преобразованием между ними в обработчике Domain Event.**

**Domain Event** — внутреннее событие, приватное для сервиса:

```csharp
// Koto.Domain — нет внешних зависимостей
public interface IDomainEvent { }

// Насыщенные доменные данные, включая Value Objects
public sealed record OrderPlacedDomainEvent(
    OrderId OrderId,
    CustomerId CustomerId,
    Money TotalAmount,       // Value Object — внутренний тип
    IReadOnlyList<OrderLine> Lines
) : IDomainEvent;
```

**Integration Event** — публичный контракт для других сервисов:

```csharp
// Koto.Application — публичный, стабильный контракт
public interface IIntegrationEvent
{
    Guid EventId { get; }
    DateTimeOffset OccurredAt { get; }
    string? CorrelationId { get; }
}

// Плоская схема с примитивами — никаких внутренних типов
public sealed record OrderPlacedIntegrationEvent(
    Guid EventId,
    DateTimeOffset OccurredAt,
    string? CorrelationId,
    Guid OrderId,
    Guid CustomerId,
    decimal Total            // примитив, не Money VO
) : IIntegrationEvent;
```

**Явная трансляция** происходит в обработчике Domain Event:

```csharp
public class OrderPlacedDomainEventHandler
{
    public async Task HandleAsync(OrderPlacedDomainEvent evt, IIntegrationEventPublisher publisher)
    {
        // Явное отображение — выбираем, что открывать наружу
        await publisher.PublishAsync(new OrderPlacedIntegrationEvent(
            EventId: Guid.NewGuid(),
            OccurredAt: DateTimeOffset.UtcNow,
            CorrelationId: evt.CorrelationId,
            OrderId: evt.OrderId.Value,
            CustomerId: evt.CustomerId.Value,
            Total: evt.TotalAmount.Amount     // примитив, не Money VO
        ));
    }
}
```

### Аргументация

| Критерий | Обоснование |
|---|---|
| Независимость эволюции | Domain Event можно менять свободно: добавлять поля, переименовывать, рефакторить. Integration Event — публичный API; любое ломающее изменение требует новой версии события |
| Предотвращение утечки домена | Money, OrderLine и другие Value Objects — внутренние типы. Публикация Domain Event напрямую обнажала бы внутреннюю доменную модель снаружи |
| Видимая архитектурная граница | Обработчик-трансформер — явная точка связи. Разработчик сразу видит, где заканчивается внутреннее и начинается внешнее |
| Избирательная публикация | Обработчик Domain Event сам решает, нужно ли порождать Integration Event. Некоторые внутренние события вообще не выходят наружу |
| Идемпотентность и трассировка | Integration Event несёт `EventId`, `OccurredAt`, `CorrelationId`, необходимые для надёжной доставки. Domain Event этого не требует |
| Размещение в слоях | `IDomainEvent` в `Koto.Domain` (без внешних зависимостей); `IIntegrationEvent` в `Koto.Application` — соответствует принципу ADR-001 |

#### Последствия

**✅ Положительные:**
- Domain Events развиваются свободно: рефакторинг внутренней модели не затрагивает внешние потребители
- Integration Events остаются минимальными и стабильными: потребители получают только то, что им нужно
- Граница между сервисами делается явной и легко находимой при ревью кода
- Добавление `EventId` в Integration Events обеспечивает идемпотентную обработку на стороне потребителей
- Обработчики могут применять бизнес-логику при трансляции: фильтровать, обогащать, объединять несколько Domain Events в один Integration Event

**⚠️ Негативные:**
- Необходимо писать и поддерживать код трансляции в каждом обработчике
- Два отдельных класса для «одного и того же события» поначалу может казаться избыточным новым участникам
- При изменении Domain Event нужно вручную проверять, нужно ли обновлять и Integration Event

**↗️ Зависимости:**
- Wolverine Outbox обеспечивает атомарность: бизнес-данные и Domain Event сохраняются в одной транзакции, и доставка гарантирована даже при сбое
- `IIntegrationEventPublisher` (в `Koto.Application`) абстрагирует транспорт и реализуется в `Koto.Infrastructure` поверх Kafka
- ADR-001 (нулевые внешние зависимости в `Koto.Domain`) остаётся в силе: `IDomainEvent` — чистый C#-интерфейс без атрибутов сериализации

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Единый тип события для обоих сценариев** | Меньше кода; нет шага трансляции | Внутренний и внешний контракты неразрывно связаны; изменение доменной модели ломает потребителей в других сервисах | Нарушает принцип независимой эволюции; делает рефакторинг домена опасным |
| **Публикация Domain Events напрямую в Kafka** | Ещё меньше кода; автоматическое распространение всех изменений | Обнажает внутреннюю доменную модель; нет контроля над публичным API; версионирование становится хаотичным | Нарушает инкапсуляцию; принуждает к немедленному версионированию при любом внутреннем рефакторинге |
| **Только Integration Events, без Domain Events** | Единственный тип событий; нет дублирования | Теряются преимущества in-process обработки событий; Outbox применяется к событиям, не предназначенным для Kafka | Смешивает внутреннюю реактивность с межсервисной коммуникацией; архитектурная разница становится неявной |
| **Наследование: IntegrationEvent расширяет DomainEvent** | Выглядит «элегантно»; переиспользование полей | Неверная семантика — это разные концепции, а не разновидности одного понятия; создаёт путаницу в иерархии типов; усложняет сериализацию | Неправильная концептуальная модель; иерархия наследования размывает архитектурную границу |

### 5. Риски

1. **Дрейф между Domain Event и Integration Event**  
   При изменении Domain Event разработчик может забыть оценить, нужно ли менять соответствующий Integration Event.  
   *Меры:* Хранить обработчики Domain Events рядом с Integration Events в одном каталоге (`Features/<Feature>/Events/`). Включить в чеклист PR: «Менялись ли Domain Events? Проверь соответствующие Integration Events».

2. **Рост числа классов событий**  
   По мере роста системы количество пар Domain/Integration событий может стать значительным.  
   *Меры:* Принять как норму — каждая пара отражает явное архитектурное решение. При необходимости добавить генератор кода или source generator для шаблонного кода трансляции.

3. **Неверное версионирование Integration Events**  
   Ломающее изменение схемы Integration Event без создания новой версии нарушит работу потребителей.  
   *Меры:* Принять конвенцию именования: `OrderPlacedIntegrationEventV2`. Добавить контрактные тесты (consumer-driven contract tests) между сервисами-производителями и потребителями. Задокументировать правила версионирования в CONTRIBUTING.md.

4. **Сложность Outbox при высокой нагрузке**  
   Таблица Outbox Wolverine может стать узким местом при большом объёме Domain Events.  
   *Меры:* Отслеживать размер очереди Outbox в мониторинге. При необходимости перейти на партиционирование таблицы Outbox или выделить отдельный сервис-диспетчер. Данный ADR описывает архитектурное решение; оптимизация производительности — отдельная задача.
