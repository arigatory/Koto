# ADR-012: Поддержка двух архитектурных стилей — Clean Architecture и Vertical Slice Architecture

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В .NET-экосистеме микросервисов сложились два доминирующих архитектурных стиля, каждый из которых имеет сильную базу практиков и проверенные на практике подходы.

**Clean Architecture (Onion / Hexagonal)** организует код по слоям ответственности:

```
YourService.Domain/         — агрегаты, Value Objects, доменные события
YourService.Application/    — команды, запросы, обработчики, обработчики событий
YourService.Infrastructure/ — EF Core, HTTP-клиенты, Kafka
YourService.Api/            — FastEndpoints, middleware
```

Сильные стороны: явная изоляция доменной логики, удобна для команд с глубоким DDD-бэкграундом, хорошо масштабируется при росте сложности предметной области.

**Vertical Slice Architecture** группирует код по бизнес-фичам, а не по слоям:

```
YourService/Features/
  PlaceOrder/
    PlaceOrderCommand.cs     — все слои одной фичи в одной папке
    PlaceOrderHandler.cs
    PlaceOrderEndpoint.cs
    PlaceOrderValidator.cs
  Domain/                    — общие агрегаты
  Infrastructure/            — общая инфраструктура
```

Сильные стороны: фичи разрабатываются независимо, минимальная связность между слайсами, особенно удобна для крупных команд и микросервисов с чётко очерченными независимыми фичами.

На момент принятия решения Koto-стек не имел явной позиции по выбору архитектурного стиля. Это создавало неопределённость: одни команды выбирали Clean Architecture, другие — Vertical Slice, причём строительные блоки Koto использовались по-разному в каждом случае. Возникла необходимость либо стандартизировать один стиль, либо официально поддержать оба, обеспечив шаблоны и примеры для каждого.

## 2. Требования

### Функциональные

| Категория | Требование |
|---|---|
| Шаблон scaffolding | `dotnet new koto-microservice` должен поддерживать параметр `--arch clean` и `--arch slice` для генерации соответствующей структуры проекта |
| Строительные блоки | `Entity`, `AggregateRoot`, `ICommand`, `ICqrsDispatcher` и другие примитивы Koto должны работать идентично в обоих архитектурных стилях без каких-либо изменений в API |
| Примеры (samples) | Репозиторий Koto должен содержать два sample-проекта на основе одного домена: `OrderFlow.CleanArch` и `OrderFlow.VerticalSlice` — для прямого сравнения |
| Документация | Для каждого стиля должна быть опубликована руководящая документация с описанием рекомендуемой структуры папок, соглашений об именовании и примерами регистрации зависимостей |
| Правило зависимостей | Независимо от выбранного стиля должно соблюдаться единое правило зависимостей: Domain → Application → Infrastructure (только Infrastructure знает о EF Core, Wolverine, HTTP) |

### Нефункциональные

| Категория | Требование | Критичность |
|---|---|---|
| Нейтральность строительных блоков | Пакеты `Koto.Domain` и `Koto.Application` не должны накладывать ограничений на физическую структуру проекта | Обязательно |
| Изоляция доменной логики | Независимо от архитектурного стиля, доменный код не должен иметь зависимостей от фреймворков (EF Core, ASP.NET, Wolverine) | Обязательно |
| Скорость onboarding | Разработчик, знакомый с одним из стилей, должен уметь запустить соответствующий шаблон и получить рабочий проект без изучения нового подхода | Высокая |
| Консистентность примеров | Оба sample-проекта должны реализовывать один и тот же сценарий (OrderFlow), чтобы разница была сведена исключительно к организации кода | Высокая |
| Поддерживаемость шаблонов | Шаблоны должны поддерживаться в актуальном состоянии при обновлении Koto-пакетов | Средняя |

---

## 3. Решение

### Описание

**Koto-стек официально поддерживает оба архитектурных стиля — Clean Architecture и Vertical Slice Architecture — как равнозначные и одинаково поддерживаемые варианты.**

Строительные блоки Koto (`Entity`, `AggregateRoot`, `ICommand`, `ICqrsDispatcher` и др.) не привязаны ни к одному из стилей и работают идентично в обоих случаях. Выбор архитектурного стиля влияет исключительно на физическую организацию файлов и папок — но не на API строительных блоков, не на семантику команд и запросов, и не на поведение инфраструктурных компонентов.

**Шаблон `dotnet new koto-microservice`** поддерживает параметр `--arch`:

```bash
dotnet new koto-microservice --arch clean   # Clean Architecture
dotnet new koto-microservice --arch slice   # Vertical Slice
```

Шаблон `--arch clean` генерирует стандартную четырёхпроектную структуру:

```
YourService.Domain/
YourService.Application/
YourService.Infrastructure/
YourService.Api/
```

Шаблон `--arch slice` генерирует структуру на основе фич:

```
YourService/
  Features/
    <FeatureName>/
      <FeatureName>Command.cs
      <FeatureName>Handler.cs
      <FeatureName>Endpoint.cs
      <FeatureName>Validator.cs
  Domain/
  Infrastructure/
```

**Правило зависимостей, обязательное для обоих стилей:**

Независимо от выбранной структуры папок, инверсия зависимостей остаётся неизменной:
- Доменная логика не имеет зависимостей на фреймворки (zero dependencies rule).
- Application-слой не знает об EF Core, Wolverine, HTTP-клиентах.
- Только Infrastructure-слой содержит конкретные реализации: репозитории EF Core, Wolverine-транспорты, HTTP-клиенты.

**Sample-проекты для прямого сравнения:**

Репозиторий содержит два sample-проекта, реализующих один и тот же домен (OrderFlow):
- `samples/OrderFlow.CleanArch` — тот же домен в Clean Architecture.
- `samples/OrderFlow.VerticalSlice` — тот же домен в Vertical Slice Architecture.

Такой подход позволяет командам сравнить оба стиля на реальном примере и принять обоснованное решение.

### Аргументация

| Критерий | Обоснование |
|---|---|
| Разные потребности команд | Команды с глубоким DDD-бэкграундом предпочитают Clean Architecture; крупные команды с независимыми фичами выигрывают от Vertical Slice. Навязывание одного стиля снижает adoption и создаёт трения там, где их можно избежать |
| Строительные блоки не зависят от структуры | `Entity`, `AggregateRoot`, `ICommand` и остальные примитивы Koto не имеют мнения о физической организации кода. Поддержка обоих стилей не добавляет технического долга в ядро библиотек |
| Clean Architecture оптимальна для сложных доменов | Когда предметная область богата бизнес-правилами и инвариантами, явная изоляция Domain-слоя снижает риск его засорения инфраструктурными деталями |
| Vertical Slice оптимальна для независимых фич | Когда команда работает над изолированными фичами микросервиса, группировка по фичам минимизирует merge-конфликты и облегчает навигацию по коду |
| Правило зависимостей остаётся единым | Выбор стиля — это выбор организации файлов, а не выбор семантики зависимостей. Единое правило зависимостей, применяемое к обоим стилям, сохраняет архитектурную целостность |
| Снижение барьера входа | Разработчик, уже знакомый с одним из стилей, начинает работать с Koto-стеком без необходимости переучиваться, что ускоряет adoption |

#### Последствия

**Положительные:**
- Команды используют архитектурный стиль, который им знаком, что снижает когнитивную нагрузку и ускоряет разработку.
- Koto-стек становится привлекательным для широкого круга команд, независимо от их архитектурных предпочтений.
- Наличие двух sample-проектов на одном домене создаёт практический обучающий материал, наглядно демонстрирующий разницу между стилями.
- Строительные блоки остаются нейтральными и не обрастают специфической логикой для конкретного стиля.

**Негативные:**
- Поддержка двух шаблонов и двух sample-проектов требует дополнительных усилий при обновлении Koto-пакетов.
- Отсутствие единственного «официального» стиля может создавать неопределённость при онбординге новых разработчиков в уже существующий проект.
- При code review необходимо явно проверять соблюдение правила зависимостей — оно не гарантируется автоматически в Vertical Slice, где все файлы фичи находятся в одной папке.

**Зависимости:**
- `Koto.Templates` — NuGet-пакет с шаблонами `dotnet new`; должен содержать оба варианта `--arch clean` и `--arch slice`.
- `samples/OrderFlow.CleanArch` и `samples/OrderFlow.VerticalSlice` — оба sample-проекта должны поддерживаться в актуальном состоянии.
- Документация Koto — раздел «Architecture Styles» должен описывать оба подхода с рекомендациями по выбору.
- Все последующие ADR, описывающие конкретные паттерны (репозитории, CQRS, outbox), должны содержать примеры применения для обоих стилей.

### 4. Альтернативы

| Вариант | Плюсы | Минусы | Почему отклонён |
|---|---|---|---|
| **Только Clean Architecture** | Единый стандарт; проще поддерживать один шаблон и одну документацию; хорошо известна DDD-сообществу | Не подходит для крупных команд с независимыми фичами; снижает adoption среди команд, привыкших к Vertical Slice; навязывает избыточную структуру для простых микросервисов | Ограничивает adoption без архитектурных преимуществ для строительных блоков Koto |
| **Только Vertical Slice** | Современный подход; хорошо масштабируется для крупных команд; минимальные merge-конфликты | Clean Architecture остаётся доминирующим стилем в .NET DDD-сообществе; вызовет сопротивление у команд с DDD-бэкграундом; сложнее обеспечить изоляцию Domain-слоя | Игнорирует реальное доминирование Clean Architecture и потребности DDD-ориентированных команд |
| **Собственная Koto-архитектура** | Полный контроль; можно оптимизировать под строительные блоки Koto | Разработчики уже знают Clean Architecture и Vertical Slice; значительные инвестиции в документацию и обучение; высокий риск отказа от adoption | Изобретение велосипеда там, где уже есть два хорошо понятых и проверенных паттерна |
| **Архитектурный стиль как runtime-конфигурация** | Максимальная гибкость | Нет практического смысла: выбор стиля влияет только на организацию файлов, а не на поведение кода; усложняет шаблон без выгоды | Архитектурный стиль — решение команды, а не параметр конфигурации приложения |

### 5. Риски

1. **Разрыв правила зависимостей в Vertical Slice**  
   В Vertical Slice все файлы одной фичи находятся в одной папке, что технически упрощает случайное добавление EF Core-зависимости прямо в Handler рядом с доменным кодом.  
   *Меры:* Включить в шаблон `--arch slice` анализатор зависимостей (например, через `NetArchTest` или `ArchUnitNET`), который проверяет соблюдение правила в CI. Зафиксировать правило в `CONTRIBUTING.md` проекта. Добавить явную проверку в code review checklist.

2. **Расхождение между sample-проектами**  
   При обновлении Koto-пакетов один из sample-проектов может быть обновлён с задержкой, что приведёт к несоответствию между примерами.  
   *Меры:* Включить оба sample-проекта в один CI-пайплайн и запускать тесты для обоих при каждом релизе Koto. Назначить владельца, ответственного за синхронность sample-проектов.

3. **Неопределённость при выборе стиля для новых проектов**  
   Поддержка двух равнозначных стилей может создавать «паралич выбора» у команд, начинающих новый микросервис.  
   *Меры:* Опубликовать в документации Koto явное дерево решений: «Если домен сложный и команда имеет DDD-бэкграунд → Clean Architecture; если фичи независимы и команда крупная → Vertical Slice». Добавить это дерево решений в README шаблона.

4. **Двойные затраты на поддержку шаблонов**  
   Два шаблона требуют двойных усилий при изменении структуры строительных блоков Koto или при обновлении зависимостей.  
   *Меры:* Максимально параметризовать общую часть шаблонов, вынеся shared-код (регистрация DI, конфигурация Wolverine, настройки EF Core) в повторно используемые фрагменты. Покрыть шаблоны smoke-тестами в CI.

5. **Риск «смешения» стилей внутри одного проекта**  
   Команда может начать проект в Clean Architecture и постепенно добавлять Vertical Slice-подход к новым фичам, получая гибрид без чётких правил.  
   *Меры:* Задокументировать, что смешение стилей в одном микросервисе не поддерживается Koto-шаблонами и не рекомендуется. Обратить на это внимание в документации и code review checklist. Если команда всё же выбирает гибридный подход — это явное отклонение от ADR, требующее фиксации в локальном ADR проекта.
