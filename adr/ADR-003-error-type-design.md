# ADR-003: Дизайн типа ошибки — Code + Message, без enum ErrorType, dot-notation коды

**Статус:** ✅ Принято  
**Дата:** 2026-05-10  

---

## 1. Контекст

В системе используется Result-паттерн для моделирования ожидаемых ошибок на уровне домена. Необходимо определить, какую структуру должен иметь тип `Error`: какие поля содержать, как идентифицировать категорию ошибки, как обеспечить машинную обработку и читаемость без утечки инфраструктурных концепций (HTTP, исключения) в доменный слой.

Ключевые вопросы:
- Нужен ли enum для категоризации ошибок (Validation, NotFound, Conflict и т.д.)?
- Как форматировать коды ошибок для единообразия между сервисами?
- Где хранить общие (cross-service) ошибки, а где — специфичные для сервиса?

---

## 2. Требования

### Функциональные

| # | Требование |
|---|------------|
| F1 | Ошибка должна быть машиночитаемой: возможность программной маршрутизации (например, маппинг в HTTP-статус) без switch по enum |
| F2 | Ошибка должна быть человекочитаемой: понятный смысл без обращения к документации |
| F3 | Общие ошибки (`general.*`) должны быть доступны из единой точки для всех сервисов |
| F4 | Сервис-специфичные ошибки должны определяться локально, без изменения общего кода |
| F5 | Ошибка должна поддерживать сериализацию для логирования и передачи через границы сервисов |

### Нефункциональные

| # | Требование |
|---|------------|
| NF1 | Нет связанности (coupling): добавление новой категории ошибок не должно требовать изменения общего enum |
| NF2 | Доменная чистота: тип `Error` не должен содержать HTTP-концепций (статус-коды, ProblemDetails) |
| NF3 | Единообразие: формат кода ошибки одинаков во всех сервисах системы |
| NF4 | Минимализм: структура `Error` проста и не несёт избыточных полей (severity, category и т.п.) |

---

## 3. Решение

### Описание

`Error` — простая запись (sealed record) с двумя строковыми полями: `Code` и `Message`. Никакого enum, никакого поля severity или category.

```csharp
public sealed record Error(string Code, string Message)
{
    public string Serialize() => $"{Code}::{Message}";
}
```

**Формат кода ошибки** — dot-notation, иерархический:

```
{сервис-или-general}.{сущность-или-раздел}.{описание-в-kebab-case}
```

Примеры:

```
general.value.is-required
general.value.invalid-length
general.entity.not-found
orders.order.already-cancelled
orders.order-item.quantity-exceeds-stock
payments.charge.insufficient-funds
```

**Общие ошибки** (`general.*`) размещаются в статическом классе `Errors.General`:

```csharp
public static class Errors
{
    public static class General
    {
        public static Error ValueIsRequired(string? field = null) =>
            new("general.value.is-required", ...);

        public static Error NotFound(string entity, object? id = null) =>
            new("general.entity.not-found", ...);

        public static Error InvalidLength(int min, int max) =>
            new("general.value.invalid-length", ...);
    }
}
```

**Сервис-специфичные ошибки** определяются локально в своём домене:

```csharp
// В проекте OrderService.Domain:
public static class OrderErrors
{
    public static Error AlreadyCancelled() =>
        new("orders.order.already-cancelled", "Order is already cancelled.");
}
```

**Маппинг в HTTP-статус** выводится из кода строковыми паттернами (без enum):

```
*.not-found        → 404
general.value.*    → 400
*.already-*        → 409
*.insufficient-*   → 422
```

### Аргументация

| Аспект | Обоснование |
|--------|-------------|
| Нет enum ErrorType | Код сам несёт смысл; enum создаёт coupling — каждый потребитель обязан знать значения нашего enum; добавление новой категории требует изменения общего типа |
| Dot-notation коды | Иерархическая структура (сервис → сущность → ошибка) даёт машиночитаемость через `startsWith`/regex и человекочитаемость без документации |
| Два поля (Code + Message) | Минимально необходимый набор; избыточные поля (severity, category, source) усложняют тип и нарушают принцип единственной ответственности |
| `general.*` — отдельный класс | Единая точка входа для cross-service ошибок; изолированы от доменной логики конкретных сервисов |
| Сервис-специфичные ошибки — локально | Полная автономность сервиса; изменения не затрагивают другие команды и проекты |
| `Serialize()` метод | Единый формат для логирования и передачи через границы; `Code::Message` легко парсится |

#### Последствия

**Положительные:**
- Добавление новой категории ошибок в любом сервисе — только локальное изменение, без правки общего кода.
- Маппинг в HTTP-статус реализуется в инфраструктурном слое через строковые паттерны, не загрязняя домен.
- Код ошибки читается без контекста: `orders.order.already-cancelled` понятен сам по себе.
- Лёгкая сериализация и десериализация для межсервисного взаимодействия.

**Отрицательные:**
- Нет compile-time проверки допустимых значений кода — опечатка в строке не обнаружится на этапе компиляции.
- Маппинг паттернов (код → HTTP-статус) требует соглашения и дисциплины команды для поддержания консистентности.
- Без документации или линтера сложно гарантировать соблюдение dot-notation формата во всех сервисах.

**Зависимости:**
- Все сервисы системы должны придерживаться единого соглашения по dot-notation формату кодов.
- Инфраструктурный слой (API) отвечает за маппинг кодов в HTTP-статусы; доменный слой об этом не знает.
- Класс `Errors.General` поставляется как часть общей библиотеки (`libs`), доступной всем сервисам.

## 4. Альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| `ErrorType` enum (Validation / NotFound / Conflict / Unexpected) | Создаёт жёсткий coupling: добавление новой категории требует изменения общего enum и пересборки всех зависимых сервисов; не масштабируется при росте числа доменов |
| Exception-based ошибки (`ErrorException`) | Антипаттерн для ожидаемых доменных ошибок; исключения предназначены для исключительных (неожиданных) ситуаций; нарушает flow-based обработку ошибок через Result |
| Строковые коды без соглашения о формате | Неконсистентность между сервисами; невозможно строить единые маппинги и инструменты без общего формата |
| `HttpStatusCode` как тип ошибки | Утечка HTTP-концепций в доменный слой; домен не должен знать о транспортном протоколе |
| `ProblemDetails` (RFC 7807) в домене | Утечка API-концепций в доменный слой; `ProblemDetails` — контракт HTTP-ответа, а не доменная модель |

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Несоблюдение dot-notation формата в новых сервисах | Средняя | Среднее | Добавить lint-правило или unit-тест, проверяющий формат кода при регистрации ошибки; документировать соглашение в CLAUDE.md / ADR |
| Опечатка в строковом коде ошибки | Средняя | Низкое | Определять коды только через статические методы (не inline-строки); покрывать конструкторы ошибок unit-тестами |
| Рассинхронизация маппинга паттернов (код → HTTP) | Низкая | Высокое | Централизовать маппинг в одном месте инфраструктурного слоя; покрывать тестами все зарегистрированные коды |
| Дублирование general-ошибок в разных сервисах | Низкая | Среднее | Обязательное использование `Errors.General` для cross-service случаев; code review политика |

## Ревизия 2026-07-04 (v0.3.0-preview.1)

- **`Error.Field`** — новое опциональное свойство (`string? Field { get; init; }`): имя поля/свойства, к которому относится ошибка. Заполняется **application-слоем** (validation pipeline), доменные фабрики обычно оставляют `null`. Используется HTTP-слоем для validation problem details (`errors` dictionary по полям). Доменная чистота сохранена: `Field` — имя свойства модели, не HTTP-концепция.
- **`Serialize()` удалён.** Формат `"code::message"` был транспортным хаком для FluentValidation v7: структурная ошибка ехала строкой в `ErrorMessage` без возможности обратного разбора. Начиная с FV12 доменный `Error` передаётся через `ValidationFailure.CustomState` (+ `ErrorCode`), структура не теряется (см. ревизию ADR-009). Требование F5 (сериализация для логов) покрывается сериализацией record-а как такового (JSON), выделенный строковый формат не нужен.
- Централизованный маппинг «код → HTTP-статус» из раздела «Решение» теперь реализован библиотекой: `KotoHttpErrorOptions` в пакете `Koto.Api.AspNetCore` (см. ADR-020); незамапленные бизнес-коды дают 422, а не 500.
