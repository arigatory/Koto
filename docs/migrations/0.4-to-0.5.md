# Migrating from Koto 0.4 to 0.5

Koto 0.5.0-preview.1 replaces the error model of the 0.4 line ([ADR-026](../../adr/ADR-026-error-model-and-envelope.md)).
Everything else keeps its API: aggregates, value objects, strongly-typed IDs, repositories, the
dispatcher, Wolverine/Kafka messaging, Marten event sourcing, observability, scheduling.

Five packages have **no source changes** and are republished with the new version number only:
`Koto.Messaging.Wolverine`, `Koto.Messaging.Wolverine.Postgres`, `Koto.Observability`,
`Koto.Scheduling`, `Koto.Testing.Integration`.

This guide lists every change with the 0.4 code on top and the 0.5 code below. The full change list
per release (in Russian) is in [`PLAN.md`](../../PLAN.md); coding agents get the same steps as a
checklist in the [Koto skill](../../skills/koto/references/error-model.md).

## Before you start

- Upgrade **every** `Koto.*` package at once and keep them on the same version. The line is a
  preview: `dotnet add package Koto.Domain --prerelease`, or `Version="0.5.0-preview.1"` in the
  project files.
- Work layer by layer in the order of the sections below: Domain → Application → Validation → API →
  clients → persistence → tests. Most of the migration is compile errors; fix one layer, build, move on.
- Six changes are **not** caught by the compiler. Check each of them before you deploy:
  1. The HTTP response body changed shape, for success and failure alike, and void commands answer
     `200` instead of `204` ([§4](#4-http-api-kotoapiaspnetcore-kotoapifastendpoints), [§5](#5-clients)).
  2. `AddKotoApplication` throws at startup when a command or query in the scanned assemblies has no
     handler ([§2](#2-kotoapplication--handlers-return-appresultt)).
  3. `EfCoreUnitOfWork.CommitAsync` throws when aggregates raised domain events and no Wolverine
     outbox is registered; 0.4 dropped the events silently ([§7](#7-persistence-kotoinfrastructureefcore-kotoeventsourcingmarten)).
  4. Plain FluentValidation rules report the code `validation.rule.failed` instead of the
     FluentValidation error code such as `NotEmptyValidator` ([§3](#3-kotovalidation)).
  5. In Development the API throws when a handler returned a bare error although a fuller typed
     error exists for it (`EnrichmentGuard`, [§4](#4-http-api-kotoapiaspnetcore-kotoapifastendpoints)).
  6. Marten moved from 8.37 to 9.58 ([§7](#7-persistence-kotoinfrastructureefcore-kotoeventsourcingmarten)).

## At a glance

| Area | 0.4 | 0.5 |
|---|---|---|
| Error | `new Error("code", "message") { Field = … }` | `abstract record Error(Code, Message)`: every error is a `sealed record` in a catalog |
| Error codes | any string | ≥ 3 kebab-case segments, validated when the error is constructed |
| Domain result | `Result<T>`: `Error`, `Errors : IReadOnlyList<Error>` | `Result<T>`: `FirstError`, `Errors : ErrorList<Error>` |
| Handlers, dispatcher | `Task<Result<T>>` | `Task<AppResult<T>>`, errors are `EnrichedError` |
| Leaving a handler | `return result.Error;` | `return result.Errors.ForField("…")` / `.Enrich()` / `.Enrich(map)` |
| Field of an error | `Error.Field` | `EnrichedError.Field` |
| Validation behavior | registered by `AddKotoValidation` | `o.AddValidationBehavior()` in the options chain |
| HTTP success | bare DTO, `204` for void commands | `Envelope<T>`, `200` with `result: null` for void commands |
| HTTP failure | RFC 7807 Problem Details + `errorCode` / `errorCodes` | `Envelope` with `errors[]` |
| Status mapping | `KotoHttpErrorOptions`: `Map`, `MapSuffix`, `MapPrefix` | `KotoApiOptions`: `Map(code, status)`, `Map(rule)` |
| FastEndpoints | `app.UseFastEndpoints()`; `HandleAsync` → `SendCommandAsync` | `app.UseKotoFastEndpoints()`; `Configure()` only |
| Calling another service | ad-hoc `general.conflict`, `general.validation`, … | `RemoteError` with the remote code; `HttpErrors` catalog |
| EF Core | events lost without outbox; `Specification<T>` | `CommitAsync` throws; specifications removed |
| Marten | 8.37 | 9.58 |

## 1. Koto.Domain — errors become records

### Define errors as types

`Error` is abstract. Every error is a record whose properties are its guaranteed data; they reach
clients as `details` and C# code pattern-matches on the type.

```csharp
// 0.4
public static class OrderErrors
{
    public static Error NotFound(OrderId id) => new("orders.order.not-found", $"Order {id} was not found.");
    public static readonly Error AlreadyPaid = new("orders.order.already-paid", "The order is already paid.");
}
```

```csharp
// 0.5 — one record per error, in the layer that detects the condition
public sealed record OrderNotFound(OrderId Id) : Error("orders.order.not-found", $"Order {Id} was not found.");
public sealed record OrderAlreadyPaid() : Error("orders.order.already-paid", "The order is already paid.");
public sealed record MeetupFull(int Capacity) : Error("events.meetup.full", $"The meetup is full ({Capacity} seats).");
```

Rules that changed with it:

- **Codes have at least three kebab-case segments** (`context.entity.problem`), pattern
  `^[a-z0-9]+(?:-[a-z0-9]+)*(?:\.[a-z0-9]+(?:-[a-z0-9]+)*){2,}$`. A code like `orders.not-found`
  compiles but throws `ArgumentException` the first time the record is constructed, so add the
  catalog test from [§8](#8-tests-kototesting) before anything else.
- **Shared errors are constructed, not called**, and four of their codes changed:

| 0.4 | 0.5 |
|---|---|
| `Errors.General.ValueIsRequired()` → `general.value.is-required` | `new Errors.General.ValueIsRequired()` → `general.value.is-required` |
| `Errors.General.InvalidLength(min, max)` → `general.invalid-length` | `new Errors.General.InvalidLength(min, max)` → `general.value.invalid-length` |
| `Errors.General.NotFound("order", id)` → `general.not-found` | `new Errors.General.NotFound("order", id)` → `general.entity.not-found` |
| `Errors.General.CollectionIsTooSmall(min, actual)` → `general.collection-is-too-small` | `new Errors.General.CollectionIsTooSmall(min, actual)` → `general.collection.too-small` |
| `Errors.General.CollectionIsTooLarge(max, actual)` → `general.collection-is-too-large` | `new Errors.General.CollectionIsTooLarge(max, actual)` → `general.collection.too-large` |

- `Error.Field` no longer exists on the domain error. A field belongs to the request, so it is set in
  the handler with `ForField` ([§2](#2-kotoapplication--handlers-return-appresultt)) or by the
  validation behavior.

### `Result<T>`

| 0.4 | 0.5 |
|---|---|
| `result.Error` | `result.FirstError` — for display only (a title, a status); never propagate it |
| `return result.Error;` | `return result.Errors;` — `ErrorList<Error>` converts implicitly to any `Result<T>` |
| `Errors` is `IReadOnlyList<Error>` | `Errors` is `ErrorList<Error>` (still an `IReadOnlyList<Error>`) |
| `TapError(Action<Error>)` | `TapErrors(Action<ErrorList<Error>>)` |
| `Match(onSuccess, Func<Error, R> onFailure)` | `Match(onSuccess, Func<ErrorList<Error>, R> onFailure)`; same for `MatchAsync` |
| `IDomainService` marker interface | removed — delete the `: IDomainService` |
| `IResultFactory<TSelf>` | removed |

`Bind`, `Tap`, `Ensure`, their async variants, `Result.Success()` / `Result.Failure(…)`,
`Result.Combine`, `Result.Sequence` and `Result.Traverse` are unchanged.

```csharp
// 0.4
public static Result<Email> Create(string? value)
{
    if (string.IsNullOrWhiteSpace(value)) return Errors.General.ValueIsRequired();
    if (!value.Contains('@')) return new Error("identity.email.invalid", "Email is invalid.");
    return new Email(value);
}
```

```csharp
// 0.5
public sealed record EmailInvalid(string Value) : Error("identity.email.invalid", "Email is invalid.");

public static Result<Email> Create(string? value)
{
    if (string.IsNullOrWhiteSpace(value)) return new Errors.General.ValueIsRequired();
    if (!value.Contains('@')) return new EmailInvalid(value);
    return new Email(value);
}
```

## 2. Koto.Application — handlers return `AppResult<T>`

### Signatures

```csharp
// 0.4
public sealed class PlaceOrderHandler : ICommandHandler<PlaceOrderCommand, OrderId>
{
    public async Task<Result<OrderId>> HandleAsync(PlaceOrderCommand cmd, CancellationToken ct = default)
```

```csharp
// 0.5
public sealed class PlaceOrderHandler : ICommandHandler<PlaceOrderCommand, OrderId>
{
    public async Task<AppResult<OrderId>> HandleAsync(PlaceOrderCommand cmd, CancellationToken ct = default)
```

`ICommandHandler<TCommand>` returns `Task<AppResult<Unit>>` (`return Unit.Value;` or
`return AppResult.Success();`), `IQueryHandler<TQuery, TResult>` returns `Task<AppResult<TResult>>`,
and `ICqrsDispatcher.SendAsync` / `QueryAsync` return `AppResult` too. `AppResult<T>` carries
`EnrichedError`s: the domain error plus request context (`Field`, optional `Details`), with the
original record kept as `Inner`. All of these live in the `Koto.Application` namespace.

### Leaving the handler: three explicit verbs

There is **no implicit conversion** from `Result<T>` or `ErrorList<Error>` to `AppResult<T>`. Every
`return domainResult.Error;` becomes one of:

| Verb | Defined on | Use when |
|---|---|---|
| `.ForField(nameof(cmd.Email))` | `Error`, `ErrorList<Error>` | the error came from validating a request field |
| `.Enrich()` | `Error`, `ErrorList<Error>` | nothing to add — said explicitly |
| `.Enrich(e => e is MeetupFull f ? new MeetupFullWithAlternative(f, alt.Id) : e.Enrich())` | `ErrorList<Error>` | the handler knows more than the aggregate (a typed, fuller error) |
| `.WithDetails(("retryAfterSeconds", 42))` | `Error` | optional, non-contractual additions |

```csharp
// 0.4
var email = Email.Create(cmd.Email);
if (email.IsFailure) return email.Error with { Field = nameof(cmd.Email) };

var order = await orders.GetByIdAsync(cmd.OrderId, ct);
if (order is null) return Errors.General.NotFound("order", cmd.OrderId);

var paid = order.Pay(cmd.Amount);
if (paid.IsFailure) return paid.Error;

await uow.CommitAsync(ct);
return Unit.Value;
```

```csharp
// 0.5
var email = Email.Create(cmd.Email);
if (email.IsFailure) return email.Errors.ForField(nameof(cmd.Email));        // 1. bound to a request field

var order = await orders.GetByIdAsync(cmd.OrderId, ct);
if (order is null) return new Errors.General.NotFound("order", cmd.OrderId).Enrich();

var paid = order.Pay(cmd.Amount);
if (paid.IsFailure) return paid.Errors.Enrich();                              // 2. nothing to add

await uow.CommitAsync(ct);
return Unit.Value;                                                            // success: implicit, as before
```

A typed enrichment is a record deriving from `EnrichedError` that wraps the domain error and adds
guaranteed properties; on the wire the chain is flattened into one `details` object:

```csharp
public sealed record MeetupFullWithAlternative(MeetupFull Cause, Guid AlternativeMeetupId) : EnrichedError(Cause);

var joined = meetup.Join(user.Id);
if (joined.IsFailure)
    return joined.Errors.Enrich(e => e is MeetupFull full                     // 3. fuller typed error
        ? new MeetupFullWithAlternative(full, alternative.Id)
        : e.Enrich());
```

Application-level errors (the aggregate never sees them) are records as well:
`public sealed record EmailTaken(string Email, Guid ExistingUserId) : Error("identity.email.taken", "…");`
returned as `return new EmailTaken(cmd.Email, existing.Id).Enrich();`.

### Other changes in Koto.Application

- **Handler validation at startup.** `AddKotoApplication` throws `InvalidOperationException` when a
  command or query in the scanned assemblies has no handler, or has several. Set
  `o.ValidateHandlers = false` if handlers are registered by hand or a contracts assembly is scanned
  on purpose without its handlers.
- **`AppResult<T>` is the end of the chain.** It has `IsSuccess`, `IsFailure`, `Value`, `FirstError`,
  `Errors`, `Map`, `Match` and `MatchAsync`, and deliberately no `Bind` / `Tap` / `Ensure` /
  `TapErrors`: compose on the domain `Result<T>` and convert once, at the return.
- **`Envelope<T>` lives here**, not in the HTTP package, so a SignalR hub or a Kafka reply can
  return it: `result.ToEnvelope(timeProvider.GetUtcNow())`.
- `TransactionBehavior` still commits on success and rolls back on failure; it now reads the
  `AppResult`. `INonTransactionalCommand`, `IRepository<TAgg, TId>`, `IUnitOfWork` and
  `PagedList<T>` are unchanged.

## 3. Koto.Validation

### Registration

```csharp
// 0.4 — AddKotoValidation registered the behavior; its position among the other behaviors was implicit
builder.Services.AddKotoApplication(o => o.AddLoggingBehavior().AddTransactionBehavior(), asm);
builder.Services.AddKotoValidation(asm);
```

```csharp
// 0.5 — the chain is the execution order: Logging → Validation → Transaction
using Koto.Validation;                                                        // AddValidationBehavior is an extension method

builder.Services.AddKotoApplication(
    o => o.AddLoggingBehavior().AddValidationBehavior().AddTransactionBehavior(), asm);
builder.Services.AddKotoValidation(asm);                                      // scans IValidator<T>
```

Calling `AddKotoValidation` alone still works — the behavior is then appended after the behaviors
configured in the options, so a validation failure would open a transaction first. Validators now run
**sequentially** (0.4 ran them in parallel), so async rules may share scoped services such as a
`DbContext`.

### Rules

| 0.4 | 0.5 |
|---|---|
| `RuleFor(x => x.Email).MustBeValueObject(Email.Create)` | unchanged |
| `RuleFor(x => x.Items).ListMustContainNumberOfItems(1, 50)` | unchanged |
| `RuleFor(x => x.CustomerId).MustBeEntity(...)` | removed — load the entity in the handler and return `new Errors.General.NotFound(...).Enrich()`, or write a `MustAsync` rule |
| `RuleFor(x => x.Name).NotEmptyWithKotoError()` | `RuleFor(x => x.Name).NotEmpty()` |
| `RuleFor(x => x.Name).LengthWithKotoError(1, 100)` | `RuleFor(x => x.Name).Length(1, 100)` |

### What the client receives (behavior change)

In 0.4 a plain FluentValidation rule produced an error whose code was FluentValidation's error code
(`NotEmptyValidator`, `LengthValidator`, or your `WithErrorCode` value). In 0.5 such a rule becomes
`validation.rule.failed` with the rule's code in `details.rule`; a `MustBeValueObject` failure keeps
the domain code (`general.value.is-required`, `identity.email.invalid`, …) with the record's
properties as `details`. Every error is bound to its field. Clients that matched on
FluentValidation codes must switch to `code == "validation.rule.failed"` plus `details.rule`.

## 4. HTTP API (Koto.Api.AspNetCore, Koto.Api.FastEndpoints)

### One response shape for everything

```jsonc
// 0.4 — success: the bare DTO (200), nothing at all for void commands (204)
{ "id": "7c1e…" }

// 0.4 — one failure: RFC 7807 Problem Details with Koto extensions (application/problem+json)
{ "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5", "title": "Not Found", "status": 404,
  "detail": "'order' with ID '7c1e…' was not found.", "errorCode": "orders.order.not-found", "correlationId": "0f3c…" }

// 0.4 — several failures: Validation Problem Details, messages grouped by field
{ "title": "One or more validation errors occurred.", "status": 400,
  "errors": { "email": [ "Email is invalid." ], "phone": [ "A value is required." ] },
  "errorCodes": [ "identity.email.invalid", "general.value.is-required" ], "correlationId": "0f3c…" }
```

```jsonc
// 0.5 — success (200), void commands included
{ "success": true,  "result": { "id": "7c1e…" }, "errors": [], "correlationId": "0f3c…", "timestamp": "2026-11-08T02:11:03Z" }

// 0.5 — failure (status from the first error), always application/json
{ "success": false, "result": null,
  "errors": [ { "code": "identity.email.invalid",     "message": "Email is invalid.",     "field": "email", "details": { "value": "x" } },
              { "code": "general.value.is-required",  "message": "A value is required.", "field": "phone", "details": {} } ],
  "correlationId": "0f3c…", "timestamp": "2026-11-08T02:11:09Z" }
```

`success` is the discriminator. `errors[]` is an array — `code`, `message`, `field` (camelCase per
path segment, `items[0].name`, or `null`) and `details` (the record's properties, camelCase; `{}` when
there are none). `title`, `detail`, `status`, `type`, `errorCode`, `errorCodes` and the
field → messages dictionary are gone. `timestamp` comes from the registered `TimeProvider`.

### Status codes: `KotoHttpErrorOptions` → `KotoApiOptions`

The classes are the same as in 0.4 — exact code → custom rules → `*.not-found` 404 →
`*.already-*` / `*.conflict` 409 → `*.unauthorized` 401 → `*.forbidden` 403 → `general.*` /
`validation.*` / field-bound 400 → `422` fallback — and the first error decides when there are several.
The configuration type and two of its methods changed:

```csharp
// 0.4
builder.Services.AddKotoAspNetCore(o => o
    .Map("payments.gateway.failed", 502)
    .MapSuffix(".expired", 410)
    .MapPrefix("payments.", 502));
```

```csharp
// 0.5 — KotoApiOptions (Koto.Api.AspNetCore); AddKotoApi(o => …) takes the same options in Koto.Api.FastEndpoints
builder.Services.AddKotoAspNetCore(o => o
    .Map("payments.gateway.failed", 502)
    .Map(e => e.Code.EndsWith(".expired") ? 410 : null)
    .Map(e => e.Code.StartsWith("payments.") ? 502 : null));
```

Rules receive the `EnrichedError`; match on the original record through `Inner`:
`o.Map(e => e is EnrichedError { Inner: QuotaExceeded } ? 429 : null)`. `KotoProblemDetails` is
deleted; `AddProblemDetails()` is no longer needed, `UseKotoApi()` installs the exception handler that
turns an unhandled exception into a 500 envelope with `general.server.internal-error`.

### Minimal API and MVC

`ToHttpResult` / `ToHttpResultAsync` / `ToActionResult` / `ToActionResultAsync` accept only
`AppResult<T>` — a domain `Result<T>` must leave the handler through a verb first. Declare the envelope
as the response schema:

```csharp
// 0.4
app.MapPost("/orders", (PlaceOrderCommand cmd, ICqrsDispatcher d, HttpContext ctx, CancellationToken ct)
    => d.SendAsync(cmd, ct).ToHttpResultAsync(ctx))
   .Produces<OrderId>();
```

```csharp
// 0.5
app.MapPost("/orders", (PlaceOrderCommand cmd, ICqrsDispatcher d, HttpContext ctx, CancellationToken ct)
    => d.SendAsync(cmd, ct).ToHttpResultAsync(ctx))
   .Produces<Envelope<OrderId>>();

// MVC: Task<ActionResult<Envelope<OrderId>>> instead of Task<ActionResult<OrderId>>
```

### FastEndpoints

```csharp
// 0.4
builder.Services.AddKotoApi();
builder.Services.AddFastEndpoints();
var app = builder.Build();
app.UseKotoApi();
app.UseFastEndpoints();

public class PlaceOrderEndpoint : CommandEndpoint<PlaceOrderCommand, OrderId>
{
    public override void Configure() => Post("/orders");
    public override async Task HandleAsync(PlaceOrderCommand req, CancellationToken ct) => await SendCommandAsync(req, ct);
}
```

```csharp
// 0.5
builder.Services.AddKotoApi();                 // optional: AddKotoApi(o => o.Map("payments.gateway.failed", 502))
builder.Services.AddFastEndpoints();
var app = builder.Build();
app.UseKotoApi();
app.UseKotoFastEndpoints();                    // binding and validator failures are envelopes too (400)

public class PlaceOrderEndpoint : CommandEndpoint<PlaceOrderCommand, OrderId>
{
    public override void Configure() => Post("/orders");                      // HandleAsync is sealed
}
```

- `HandleAsync` is sealed on every base endpoint, `SendCommandAsync` / `SendQueryAsync` are gone:
  delete the overrides. `Mapped*` endpoints keep `ToCommand` / `ToQuery`.
- The base endpoints declare `Envelope<TResult>` (`Envelope<object?>` for void commands) as the
  FastEndpoints response type, so OpenAPI follows automatically. Adjust any explicit
  `Description(b => b.Produces<OrderDto>())` to `Envelope<OrderDto>`.
- Hosts that map through `IEndpointRouteBuilder` use `MapKotoFastEndpoints()` instead of
  `MapFastEndpoints()`. A hand-written `Endpoint<TRequest>` maps the result itself with the
  `Koto.Api.AspNetCore` helper: `await SendResultAsync(result.ToHttpResult(HttpContext));`.
- `Koto.Api.FastEndpoints` now references `Koto.Validation`, which brings FluentValidation
  `[12.0.0,13.0.0)` transitively. A project that pinned FluentValidation 11 next to FastEndpoints must
  move to 12.

### EnrichmentGuard (new)

At the API boundary Koto checks that a handler did not forget the fuller type: when the scanned
assemblies contain a record deriving from `EnrichedError` whose constructor takes an error of type `X`
(`MeetupFullWithAlternative(MeetupFull Cause, …)`), a bare `X` reaching the response is a violation.
Development throws `InvalidOperationException`; everywhere else a warning is logged. Override with
`o.EnrichmentGuard = EnrichmentGuardMode.Off / Warn / Throw`.

## 5. Clients

Every client of a Koto API — a TypeScript front end, a mobile app, a script — changes the same way:
branch on `success`, read `errors[]`, stop treating `204` as the void success.

```ts
// 0.4
const res = await fetch(url, init);
if (res.status === 204) return undefined;
const body = await res.json();
if (!res.ok) throw new ApiError(body.errorCode ?? body.errorCodes?.[0], body.detail ?? body.title);
return body as T;
```

```ts
// 0.5
type Envelope<T> = {
  success: boolean;
  result: T | null;
  errors: { code: string; message: string; field: string | null; details: Record<string, unknown> }[];
  correlationId: string | null;
  timestamp: string;
};

const env = (await (await fetch(url, init)).json()) as Envelope<T>;
if (!env.success) throw new ApiError(env.errors[0].code, env.errors[0].message, env.errors);
return env.result as T;
```

Form validation reads `errors.filter(e => e.field)`; retry-after style data comes from `details`
(`env.errors[0].details.retryAfterSeconds`). The HTTP status is still meaningful for infrastructure
(401 refresh flows, retries on 5xx), but application logic reacts to `code`.

## 6. Calling another Koto service (Koto.Infrastructure.Http)

`ServiceHttpClient.ReadResultAsync<T>` still returns a domain `Result<T>`, and the calling handler
enriches it like any other domain result. What it contains changed:

- A Koto **envelope** in the response is unwrapped: `result` on success, each entry of `errors[]` as a
  `RemoteError` (an `EnrichedError` with the remote `code`, `message`, `field` and `details`) on
  failure. Domain codes cross the service boundary intact —
  `if (result.FirstError.Code == "wallet.account.insufficient-funds")` works without parsing JSON. A
  malformed remote code becomes `general.remote.unknown-error` with the original in `details.remoteCode`.
- Any other body is deserialized as `T` on a success status, otherwise mapped through the
  `HttpErrors` catalog. The fallback codes changed:

| HTTP status | 0.4 | 0.5 |
|---|---|---|
| 404 | `general.not-found` | `HttpErrors.ResourceNotFound` → `general.resource.not-found` |
| 409 | `general.conflict` | `HttpErrors.ResourceConflict` → `general.resource.conflict` |
| 400 / 422 | `general.validation` (422 only) | `HttpErrors.RequestInvalid` → `general.request.invalid` (message = response body) |
| 5xx | `general.unexpected` | `HttpErrors.ServerUnexpected` → `general.server.unexpected` (`details.statusCode`) |
| other | `general.http-error` | `HttpErrors.HttpFailure` → `general.server.http-error` |
| 2xx, empty body | — | `HttpErrors.ResponseEmpty` → `general.response.empty` |

`MapErrorResponse` is still virtual for service-specific mapping. In the handler:

```csharp
var debited = await wallet.DebitAsync(cmd.AccountId, cmd.Amount, ct);        // Result<Receipt> from the remote service
if (debited.IsFailure) return debited.Errors.Enrich();                        // RemoteErrors pass through unchanged
```

## 7. Persistence (Koto.Infrastructure.EFCore, Koto.EventSourcing.Marten)

### Domain events need an outbox

`EfCoreUnitOfWork<TContext>.CommitAsync` throws `InvalidOperationException` when tracked aggregates
raised domain events and no Wolverine outbox (`IDbContextOutbox`) is registered. In 0.4 the save went
through and the events were silently lost. Either configure the outbox (`AddKotoEFCore<TContext>` +
Wolverine's `PersistMessagesWithPostgresql` / `UseEntityFrameworkCoreTransactions`, see the package
README) or register your own `IUnitOfWork` before `AddKotoEFCore`, which uses `TryAddScoped` so yours
wins:

```csharp
using Microsoft.EntityFrameworkCore.Storage;   // IDbContextTransaction

public sealed class OrderUnitOfWork(OrderDbContext db) : IUnitOfWork
{
    private IDbContextTransaction? _tx;
    public bool HasActiveTransaction => _tx is not null;
    public async Task BeginTransactionAsync(CancellationToken ct = default) =>
        _tx ??= await db.Database.BeginTransactionAsync(ct);
    public async Task CommitAsync(CancellationToken ct = default)
    {
        var events = db.ChangeTracker.Entries<IHasDomainEvents>().SelectMany(e => e.Entity.DomainEvents).ToList();
        // dispatch `events` in-process here if anything listens; KotoDbContext clears them after the save
        await db.SaveChangesAsync(ct);
        if (_tx is not null) { await _tx.CommitAsync(ct); await _tx.DisposeAsync(); _tx = null; }
    }
    public async Task RollbackAsync(CancellationToken ct = default)
    {
        if (_tx is not null) { await _tx.RollbackAsync(ct); await _tx.DisposeAsync(); _tx = null; }
    }
}
```

### Specifications are removed

`ISpecification<T>`, `Specification<T>` and `SpecificationEvaluator` are gone. Put the query where it is
used — a repository method with LINQ, or `IQueryable` straight from the `DbContext` in a query handler:

```csharp
// 0.4
var active = SpecificationEvaluator.GetQuery(db.Orders, new ActiveOrdersSpec(customerId));
```

```csharp
// 0.5
var active = db.Orders.Where(o => o.CustomerId == customerId && o.Status == OrderStatus.Active)
                      .OrderByDescending(o => o.CreatedAt);
```

`Repository<TAgg, TId>` (`GetByIdAsync`, `Add`, `Delete`), `KotoDbContext`, the strongly-typed ID
conventions and `ToPagedListAsync` are unchanged. `AddKotoEFCore` now also registers `KotoDbContext`,
so `IRepository<TAgg, TId>` resolves from DI without a workaround.

### Marten 9

`Koto.EventSourcing.Marten` references Marten **9.58** (0.4: 8.37). The package's own API is
unchanged, but a Marten major is a Marten major: re-check projections and custom `IDocumentStore`
configuration against the Marten 9 release notes.

## 8. Tests (Koto.Testing)

- Handler tests assert on `AppResult<T>` with the same fluent API as before (`using Koto.Testing.Assertions;`):
  `result.Should().BeSuccess()`, `.BeFailureWith("orders.order.not-found")`, `.HaveErrors(...)`,
  `.HaveValue(x)`, plus `.HaveErrorForField("email")` — case-insensitive, so the wire name and
  `nameof(cmd.Email)` both match.
- Add the catalog test once per service (`using Koto.Testing.Catalog;`). It constructs every error
  record with stub arguments and fails on a malformed or duplicated code; typed enrichments deriving
  from `EnrichedError` share their cause's code and are not duplicates:

```csharp
[Fact]
public void Error_catalog_is_valid() =>
    ErrorCatalog.ShouldBeValid(typeof(OrderNotFound).Assembly, typeof(PlaceOrderHandler).Assembly);
```

- Integration tests that asserted on `204`, `application/problem+json`, `errorCode` or the
  field → messages dictionary now read the envelope ([§4](#4-http-api-kotoapiaspnetcore-kotoapifastendpoints)).
- `AggregateTestFixture`, `FakeRepository`, `FakeIntegrationEventPublisher` and everything in
  `Koto.Testing.Integration` are unchanged.

## Removed API

| Removed in 0.5 | Use instead |
|---|---|
| `new Error(code, message)` | a `sealed record X(...) : Error(code, message)` in the catalog |
| `Error.Field` | `EnrichedError.Field`, set with `ForField` |
| `Result<T>.Error` | `Result<T>.FirstError` (display) / `Errors` (propagation) |
| `Result<T>.TapError` | `TapErrors` |
| `IDomainService` | nothing — delete the marker |
| `IResultFactory<TSelf>` | nothing |
| `Errors.General.X(...)` static methods | `new Errors.General.X(...)` records |
| `KotoValidators.MustBeEntity`, `NotEmptyWithKotoError`, `LengthWithKotoError` | load in the handler / `NotEmpty()` / `Length()` |
| `KotoHttpErrorOptions`, `MapSuffix`, `MapPrefix` | `KotoApiOptions`, `Map(rule)` |
| `KotoProblemDetails` | `Envelope.Fail(...)` / `ToEnvelope(...)` |
| `ToHttpResult` / `ToActionResult` on `Result<T>` | the same methods on `AppResult<T>` |
| `CommandEndpoint.SendCommandAsync`, `QueryEndpoint.SendQueryAsync`, `HandleAsync` overrides | `Configure()` only; a hand-written endpoint sends `result.ToHttpResult(HttpContext)` |
| `app.UseFastEndpoints()` with Koto endpoints | `app.UseKotoFastEndpoints()` / `MapKotoFastEndpoints()` |
| `ISpecification<T>`, `Specification<T>`, `SpecificationEvaluator` | LINQ in the repository or query handler |
| `general.not-found`, `general.conflict`, `general.validation`, `general.unexpected`, `general.http-error` (remote calls) | `HttpErrors.*` codes, [§6](#6-calling-another-koto-service-kotoinfrastructurehttp) |

## Compile errors you will see, and what they mean

| The compiler complains about… | Do |
|---|---|
| creating an instance of the abstract type `Error` | define a record for the error ([§1](#1-kotodomain--errors-become-records)) |
| `Result<T>` having no member `Error` | `FirstError` for display, `Errors` to propagate |
| no implicit conversion from `ErrorList<Error>` / `Result<T>` / `Error` to `AppResult<T>` | pick a verb: `ForField`, `Enrich()`, `Enrich(map)` ([§2](#2-kotoapplication--handlers-return-appresultt)) |
| `HandleAsync` return type not matching `Task<AppResult<…>>` | change the signature |
| `Error` having no member `Field` | `ForField` in the handler; read it from `EnrichedError.Field` |
| `Match` not accepting a `Func<Error, …>` | the callback receives `ErrorList<Error>` |
| `KotoApplicationOptions` having no `AddValidationBehavior` | `using Koto.Validation;` |
| `IApplicationBuilder` having no `UseKotoFastEndpoints` | `using Koto.Api.FastEndpoints;` |
| `KotoHttpErrorOptions`, `KotoProblemDetails`, `MapSuffix`, `MapPrefix` not found | `KotoApiOptions`, `Map(rule)` ([§4](#4-http-api-kotoapiaspnetcore-kotoapifastendpoints)) |
| `SendCommandAsync` / `SendQueryAsync` not found, `HandleAsync` cannot be overridden | delete the override |
| `Specification<T>` not found | LINQ ([§7](#7-persistence-kotoinfrastructureefcore-kotoeventsourcingmarten)) |

## Checklist

1. Bump every `Koto.*` package to `0.5.0-preview.1` (`--prerelease`).
2. **Domain:** turn each `new Error(...)` into a record; `new Errors.General.X(...)`; codes with ≥ 3
   segments; `Error` → `FirstError`, `return x.Errors;`, `TapError` → `TapErrors`, `Match` callbacks
   take the list; delete `IDomainService` / `IResultFactory`.
3. **Application:** `Task<AppResult<T>>` in handlers; every exit through `ForField` / `Enrich()` /
   `Enrich(map)`; `Error.Field` → `EnrichedError.Field`; typed enrichments for errors the handler
   can complete; decide on `ValidateHandlers`.
4. **Validation:** `AddLoggingBehavior().AddValidationBehavior().AddTransactionBehavior()` +
   `AddKotoValidation`; replace the removed helpers.
5. **API:** `KotoHttpErrorOptions` → `KotoApiOptions`; drop `AddProblemDetails` and
   `KotoProblemDetails`; `UseKotoFastEndpoints()`; endpoints implement `Configure()` only;
   `Produces<Envelope<T>>()` / `ActionResult<Envelope<T>>` in Minimal API and MVC.
6. **Remote calls:** map on `RemoteError` codes and the new `HttpErrors` codes.
7. **EF Core / Marten:** outbox or your own `IUnitOfWork` where aggregates raise events; replace
   specifications; re-check projections on Marten 9.
8. **Tests:** `AppResult` assertions; the `ErrorCatalog.ShouldBeValid` test; envelope assertions in
   integration tests.
9. **Clients:** read `success`, `errors[]`, `result`; stop expecting `204`.
10. Start the service once in Development: the handler check runs at startup, the `EnrichmentGuard`
    throws on the first response that misses a typed enrichment.
